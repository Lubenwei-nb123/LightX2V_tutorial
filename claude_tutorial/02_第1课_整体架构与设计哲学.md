## 1. 框架要解决的不是“调用一个模型”

LightX2V 同时面对四类变化：

1. **模型差异**：Wan、Qwen-Image、LTX2、HunyuanImage3、WorldMirror 等并不共享同一种输入、调度器和输出；
2. **任务差异**：文本、图像、视频、音频、动作和三维重建可能组合出现；
3. **优化差异**：量化、CPU Offload、缓存、编译、LoRA、TP、CFG 并行和 SP 不是任意组合都成立；
4. **部署差异**：同一 Runner 既可能本地端到端运行，也可能拆成 Encoder / Transformer / Decoder 角色。

因此更准确的设计概括是：

> **多入口 + 配置汇聚 + 注册路由 + Runner 编排 + 模型内部执行分层 + 平台算子注入。**

Pipeline 很重要，但它只是 Python API 的高层入口之一。命令行直接在 `lightx2v/infer.py` 中构造配置、输入和 Runner；服务 Worker 也复用 `init_runner()`，并不先创建 `LightX2VPipeline`；分离部署还有自己的控制与通信路径（`lightx2v/infer.py:50-54`、`lightx2v/server/services/inference/worker.py:38-59`、`lightx2v/disagg/disagg_mixin.py:116-157`）。

## 2. 用“职责层”而不是“三层继承树”看架构

```text
Python API                  CLI / torchrun                 Server / Disagg
LightX2VPipeline            lightx2v.infer                 Worker / Controller
      │                           │                              │
      └──────────────┬────────────┴──────────────┬───────────────┘
                     ▼                           ▼
             配置汇聚 / 输入构造           注册键解析与 Runner 创建
                     │                           │
                     └──────────────┬────────────┘
                                    ▼
                         Runner：生命周期与业务编排
                   ┌────────────────┼─────────────────┐
                   │                │                 │
             DefaultRunner     自定义 Runner      DisaggMixin
             标准扩散模板       自有主流程          通信横切能力
                   │                │                 │
                   └────────────────┼─────────────────┘
                                    ▼
                Transformer Model / Encoders / Scheduler / VAE
                                    │
                                    ▼
                  Weight Modules / Infer Modules / Platform Ops
```

这张图表达了两个重要事实：

- 上层入口最终可以汇合到 `RUNNER_REGISTER[key](config)`，但入口自己的可见模型集合、参数解析和返回处理并不完全相同；
- Runner 层是编排层，不是一个所有模型都严格遵守的模板方法继承树。

### 2.1 入口层

- `LightX2VPipeline`：适合 Python 程序中先收集配置、后反复 `generate()`（`lightx2v/pipeline.py:70-505`）；
- CLI：`argparse → set_config → init_empty_input_info → init_runner → run_pipeline`（`lightx2v/infer.py:81-326`）；
- 服务：Worker 初始化 Runner，按请求更新 `InputInfo` 和可变配置，并把结果编码为服务响应（`lightx2v/server/services/inference/worker.py:26-151`）；
- 分离部署：Runner 可借助 `DisaggMixin` 发送、接收编码结果或 latent（`lightx2v/disagg/disagg_mixin.py:116-157`）。

### 2.2 Runner 层

Runner 决定：加载哪些组件、如何把任务输入编码、如何运行主循环、如何解码和如何返回结果。`DefaultRunner` 提供扩散模型的常用模板；特化 Runner 可以只覆盖局部，也可以重写整条链。

### 2.3 Transformer Model 层

`BaseTransformerModel` 统一权重加载、量化权重、LoRA、Offload、TP 和执行模块装配；具体模型负责本模型的权重容器与推理实现（`lightx2v/models/networks/base_model.py:44-115`）。

### 2.4 组件与平台层

编码器、VAE、Scheduler、权重模块、推理模块和注意力算子各自可替换。平台实现先注册到 `lightx2v_platform`，通用注册器再显式合并一部分平台实现（`lightx2v/utils/registry_factory.py:1-4`、`lightx2v/utils/registry_factory.py:82-88`）。

## 3. Runner 不是严格单继承树

把 Runner 简化成下面这样会误导适配工作：

```text
BaseRunner → DefaultRunner → 所有具体 Runner
```

源码中至少有四种形态：

```text
BaseRunner
├── DefaultRunner
│   ├── 大量标准扩散 Runner
│   └── WanRunner(DisaggMixin, DefaultRunner)
│       └── 若干 Wan 特化 Runner
├── FastWAMRunner(BaseRunner)
└── WorldMirrorRunner(BaseRunner)
```

- `WanRunner(DisaggMixin, DefaultRunner)` 和 `QwenImageRunner(DisaggMixin, DefaultRunner)` 是多继承，Mixin 提供分离部署能力（`lightx2v/models/runners/wan/wan_runner.py:75-76`、`lightx2v/models/runners/qwen_image/qwen_image_runner.py:57-58`）；
- `FastWAMRunner` 直接继承 `BaseRunner`，执行机器人动作策略，不需要标准扩散链（`lightx2v/models/runners/wan/fastwam_runner.py:342-434`）；
- `WorldMirrorRunner` 也直接继承 `BaseRunner`，没有扩散 Scheduler，而是重建并保存多种三维产物（`lightx2v/models/runners/worldmirror/worldmirror_runner.py:131-149`）。

所以新增模型时首先要问：**它是否真的符合 DefaultRunner 的标准扩散模板？** 继承只是复用手段，不是适配目标。

## 4. BaseRunner：松散契约加统一生命周期

### 4.1 为什么称为“松散契约”

`BaseRunner` 虽然继承 `ABC`，但很多组件方法只是普通 `pass`，没有 `@abstractmethod`；`load_vae()` 甚至默认返回 `(None, None)`。这意味着 Python 不会因为某个子类没有实现所有这些方法而禁止实例化（`lightx2v/models/runners/base_runner.py:12-21`、`lightx2v/models/runners/base_runner.py:133-211`）。

它提供的是三类约定：

| 类别 | 代表方法 | 含义 |
|---|---|---|
| 组件能力 | `load_transformer`、`load_text_encoder`、`load_vae` | 使用到该组件的流程应提供实现 |
| 生命周期钩子 | `init_run`、`run_segment`、`end_run` | 标准模板在固定时机调用，子类按需覆盖 |
| 横切能力 | `check_stop`、`compute_usage` | 多数 Runner 可直接复用 |

这里的关键不是“把每个方法都实现一遍”，而是：**你的 `run_pipeline()` 实际会走到哪些能力，就保证哪些能力成立。**

### 4.2 `__init_subclass__` 自动包装两个入口

`BaseRunner.__init_subclass__()` 会在子类定义完成时检查该类自己定义的 `init_modules()` 和 `run_pipeline()`，并安装包装器（`lightx2v/models/runners/base_runner.py:26-61`）：

```python
result = init_modules_fn(self, *args, **kwargs)
if depth == 0 and not self._warmup_done:
    self.warmup()
```

```python
result = run_pipeline_fn(self, *args, **kwargs)
self._maybe_freeze_gc()
return result
```

这不是装饰器写在每个 Runner 上，而是类创建时自动完成。`_init_modules_depth` 防止“子类 `init_modules()` 调 `super()`”导致重复预热；`_warmup_done` 保证只做一次（`lightx2v/models/runners/base_runner.py:20-24`、`lightx2v/models/runners/base_runner.py:42-59`）。

需要注意异常语义：包装器只有在原函数正常返回后才执行 `_maybe_freeze_gc()`；而 `init_modules()` 用 `finally` 恢复深度，但原函数失败时不会继续预热。

### 4.3 warmup 是显式能力，不是默认保证

- `warmup=false` 时，`DefaultRunner.warmup()` 直接返回；
- 开启后，分离部署、`unload_modules` 和特征缓存会被拒绝；
- 真正的 `run_warmup()` 默认仍抛 `NotImplementedError`（`lightx2v/models/runners/default_runner.py:98-113`）；
- Wan 只对声明支持的具体类与任务执行通用预热（`lightx2v/models/runners/wan/wan_runner.py:77-107`）。

因此 `warmup` 是需要 Runner 明确支持的运行模式，不能只在 JSON 中打开就假设可用。

### 4.4 首次成功请求后的 `gc.freeze()`

`_maybe_freeze_gc()` 在首次成功 `run_pipeline()` 后先 `gc.collect()`，再把稳定对象图移入永久代，减少后续 GC 扫描；`lazy_load` 或 `unload_modules` 会跳过，因为模型对象每请求重建（`lightx2v/models/runners/base_runner.py:68-85`）。

这里的“freeze”是 Python GC 的性能策略，不是锁配置，也不意味着对象不可变。

### 4.5 usage 是估算能力

`compute_usage()` 根据 tokenizer、VAE stride、patch size 和目标尺寸估算文本、输入图像与输出图像 token；无法计算时返回 `None`（`lightx2v/models/runners/base_runner.py:250-314`）。服务 Worker 在返回内存图像时把它加入响应（`lightx2v/server/services/inference/worker.py:125-143`）。

### 4.6 Decode 角色为什么需要 `NullScheduler`

分离部署的 Decoder 角色不执行 DiT，但 `end_run()` 等通用清理仍可能调用 `scheduler.clear()`。`BaseRunner.init_scheduler()` 因此为 `disagg_mode == "decode"` 安装只带 `clear()` 的 `NullScheduler`（`lightx2v/models/runners/base_runner.py:212-218`、`lightx2v/models/schedulers/scheduler.py:4-9`）。

这是一种最小空对象模式：维持生命周期协议，而不是伪造完整调度能力。

## 5. DefaultRunner：标准链，而非全局定律

### 5.1 初始化与组件装配

`DefaultRunner.__init__()` 处理 prompt enhancer、初始化设备并调用具体 Runner 的 `init_scheduler()`（`lightx2v/models/runners/default_runner.py:86-96`）。

`init_modules()` 的标准行为是：

1. 非 lazy / unload 模式下 `load_model()`；
2. 把 Scheduler 绑定给 Transformer Model；
3. 按 `task` 绑定一个输入编码方法；
4. 锁定配置；
5. 可选执行 compile（`lightx2v/models/runners/default_runner.py:116-143`）。

`load_model()` 依次装配 Transformer、文本编码器、图像编码器、VAE，以及可选 VFI / VSR（`lightx2v/models/runners/default_runner.py:170-178`）。

### 5.2 端到端标准链

```text
run_pipeline(input_info)
│
├── 可选 prompt enhancer
├── run_input_encoder()
└── run_main()
    ├── init_run()
    │   └── scheduler.prepare(...)
    ├── for segment
    │   ├── init_run_segment()
    │   ├── run_segment()
    │   │   └── for step
    │   │       ├── scheduler.step_pre()
    │   │       ├── model.infer(inputs)
    │   │       └── scheduler.step_post()
    │   ├── VAE decode / stream decode
    │   └── end_run_segment()
    ├── process_images_after_vae_decoder()
    └── end_run()
```

对应实现位于 `lightx2v/models/runners/default_runner.py:220-254`、`lightx2v/models/runners/default_runner.py:429-478`、`lightx2v/models/runners/default_runner.py:580-595`。

这个循环把“去噪算法”和“网络前向”分开：Scheduler 在 step 前准备时间步，在 Model 前向后消费 `noise_pred` 更新 latent；Runner 只编排时序。

### 5.3 自定义链和分离部署例外

不能拿标准链机械套所有 Runner：

- Wan 本地模式大体复用标准链，但 `run_pipeline()` 会先按 `disagg_mode` 分派；Encoder 只编码并发送，Transformer 可只去噪并发送 latent，Decoder 只接收并解码（`lightx2v/models/runners/wan/wan_runner.py:411-521`）；
- LTX2 的 `run_main()` 同时处理视频 latent 和音频 latent，并可能增加上采样阶段（`lightx2v/models/runners/ltx2/ltx2_runner.py:1050-1085`）；
- HunyuanImage3 的 `run_pipeline()` 按任务直接分派文本生成或图像生成（`lightx2v/models/runners/hunyuan_image3/hunyuan_image3_runner.py:1490-1525`）；
- FastWAM 完全不经过 Scheduler / VAE，而是读取双视角图像和状态后输出动作（`lightx2v/models/runners/wan/fastwam_runner.py:417-434`）。

结论：`DefaultRunner` 是高价值默认实现，但具体 Runner 的 `run_pipeline()` 才是最终事实来源。

## 6. BaseTransformerModel：权重层与执行层双重分层

Runner 管“流程”，Transformer Model 管“DiT 如何装载和执行”。`BaseTransformerModel` 的结构可以画成：

```text
Checkpoint / quant checkpoint / LoRA
                │
                ▼
      ┌──────── Weight containers ────────┐
      │ pre_weight                        │
      │ transformer_weights               │
      │ post_weight（可选）                │
      └────────────────┬──────────────────┘
                       │ 作为参数传入
      ┌──────── Infer executors ──────────┐
      │ pre_infer                         │
      │ transformer_infer                 │
      │ post_infer                        │
      └────────────────┬──────────────────┘
                       ▼
                   noise_pred
```

### 6.1 weights 层

子类声明 `pre_weight_class`、`transformer_weight_class` 和可选 `post_weight_class`。基类负责：

- 读取原始、量化或 dummy 权重；
- 按 rank 加载或为 TP 分片；
- 创建权重容器并执行 `load()`；
- 注册、更新或移除 LoRA；
- 在 CPU / CUDA 间迁移权重（`lightx2v/models/networks/base_model.py:51-115`、`lightx2v/models/networks/base_model.py:225-319`）。

这里把“参数存储及变换”从“计算过程”分离，Offload 和量化就能在权重模块层介入。

### 6.2 infer 层

具体模型在 `_init_infer_class()` 选择 pre / transformer / post 执行器，在 `_init_infer()` 实例化并建立依赖。以 Wan 为例：缓存策略和 CPU Offload 会选择不同的 `transformer_infer_class`（`lightx2v/models/networks/wan/model.py:161-197`）。

典型前向是：

```python
pre_infer_out = self.pre_infer.infer(self.pre_weight, inputs)
x = self.transformer_infer.infer(self.transformer_weights, pre_infer_out)
noise_pred = self.post_infer.infer(x, pre_infer_out)[0]
```

见 `lightx2v/models/networks/wan/model.py:218-238`。序列并行在 pre 与 transformer 之间切分，在 transformer 与 post 之间聚合；CFG 则在更外层决定做条件、无条件还是并行前向（`lightx2v/models/networks/wan/model.py:240-280`）。

### 6.3 为什么两套都要分 pre / transformer / post

- 权重分层回答“参数在哪里、如何加载、是否量化或换入换出”；
- 推理分层回答“本步计算按什么顺序执行、在哪里切序列、在哪里接缓存”；
- 两层配对后，同一计算阶段可以拿到专属权重容器，又不必把存储策略写死在算法代码里。

新模型若能复用已有权重模块或 infer 模块，应优先复用；不要因为目录结构看起来是三段，就默认三段都要新建。

## 7. 注册机制：可变映射、import 副作用与入口可见集

### 7.1 `Register` 是 `MutableMapping`

`Register` 实现 `MutableMapping` 所需的增删查、迭代和长度，并在内部保存 `_dict`；装饰器调用最终落到 `register()`（`lightx2v/utils/registry_factory.py:1-61`）。

```python
@RUNNER_REGISTER("wan2.1")
class WanRunner(...):
    ...

runner_cls = RUNNER_REGISTER["wan2.1"]
```

它还提供 `merge()`：遇到重复键会报错，不会静默覆盖（`lightx2v/utils/registry_factory.py:63-68`）。

### 7.2 平台注册器如何合并

`lightx2v_platform.registry_factory` 定义平台侧注册器；通用侧把平台的 Attention、MM、RMSNorm、LayerNorm 和 RoPE 注册项 merge 进自己的注册器（`lightx2v_platform/registry_factory.py:66-73`、`lightx2v/utils/registry_factory.py:82-88`）。

这使上层按统一键查算子，同时允许 CUDA、NPU、XPU 等平台在导入阶段贡献实现。Runner 注册器本身不在这组 merge 中。

### 7.3 import 才会注册

装饰器在类定义执行时运行；模块没被 import，注册项就不存在。Pipeline 顶部一批 `# noqa: F401` import 的真正作用就是触发 Runner 模块加载（`lightx2v/pipeline.py:14-38`）。

```text
import runner module
      ↓
执行 class 语句
      ↓
执行 @RUNNER_REGISTER("key")
      ↓
RUNNER_REGISTER["key"] = RunnerClass
```

### 7.4 三个集合必须分开检查

适配 `model_cls` 时至少要区分：

1. **注册键集合**：源码中实际的 `@RUNNER_REGISTER(...)`；
2. **CLI choices 集合**：`--model_cls` 能否通过参数解析（`lightx2v/infer.py:83-137`）；
3. **当前入口 import 闭包**：运行该入口时，定义注册键的模块是否真的被加载。

Pipeline 和 CLI 的 import 集明显不同：CLI 导入了 Bagel、HunyuanImage3、FastWAM 等更多 Runner（`lightx2v/infer.py:9-43`），Pipeline 的显式集合较小（`lightx2v/pipeline.py:14-38`）。所以“源码里有装饰器”不等于“所有入口都可用”。

当前基线还有一个值得建立测试的漂移样例：`wan2.2_moe_audio` 出现在 Pipeline 分支和 CLI choices 中（`lightx2v/pipeline.py:94-111`、`lightx2v/infer.py:96-104`），但全仓没有同名 `@RUNNER_REGISTER`。参数可以被接受，Runner 查找时仍可能 `KeyError`。

## 8. 配置驱动：先画写入时序，再谈优先级

### 8.1 通用配置流

```text
get_default_config()
        │
        ▼
set_args2config(args)
  用 vars(args) 中非 None、非 InputInfo 字段覆盖
        │
        ▼
auto_calc_config(config)
  ① 若 config_json 字段仍存在，加载该 JSON
  ② 加载模型目录 config.json
  ③ 可选加载量化 checkpoint config.json
  ④ 规范化 / 派生字段
        │
        ▼
Runner.init_modules() → config.lock()
```

实现见 `lightx2v/utils/set_config.py:15-59`、`lightx2v/utils/set_config.py:62-404`。

### 8.2 不同入口的 JSON 不是同一条流

- **Pipeline JSON**：`create_generator(config_json=...)` 调 `set_infer_config_json()`，JSON 直接更新 Pipeline 属性；随后 `set_config(self)` 看到的是更新后的属性（`lightx2v/pipeline.py:164-213`、`lightx2v/pipeline.py:264-268`）。它与 `set_infer_config(...)` 二选一；JSON 也会覆盖此前同名的 `enable_xxx()` 属性。
- **CLI config_json**：CLI 要求 `--config_json`，路径先进入 config，`auto_calc_config()` 再打开文件并 `config.update()`（`lightx2v/infer.py:149-150`、`lightx2v/utils/set_config.py:55-62`）。

对大多数模型，可近似记为：

```text
默认值 < 入口参数 / Pipeline 属性 < 入口 JSON < 模型结构 config < 量化 config < 后续派生修正
```

但这不是无条件统一规则：Pipeline JSON 已在 `set_args2config` 之前变成属性；WorldMirror 会专门回放部分 CLI 参数；`num_iterations` 也有保留逻辑（`lightx2v/utils/set_config.py:36-51`、`lightx2v/utils/set_config.py:55-63`、`lightx2v/utils/set_config.py:98-132`）。判断冲突时，应追踪具体 key 的最后一次写入。

### 8.3 LockableDict 的准确语义

`LockableDict` 拦截字典原地修改，支持递归包装嵌套 dict、递归 lock / unlock 和临时解锁（`lightx2v/utils/lockable_dict.py:5-68`、`lightx2v/utils/lockable_dict.py:78-129`）。

```python
config["a"] = 2
config.lock()
with config.temporarily_unlocked():
    config["a"] = 3
```

必须记住两个边界：

1. 它只实现 `__getattr__`，所以 `config.a` 可读；没有把属性赋值映射到字典键，写入仍应使用 `config["a"] = ...` 或 `update()`（`lightx2v/utils/lockable_dict.py:131-138`）；
2. 这个“锁”是防止误修改的逻辑状态，不是互斥量，不提供并发同步。`temporarily_unlocked()` 期间共享对象仍可能被其他执行流看到。

另外，递归锁只直接递归 `LockableDict` 值；嵌在 list / tuple 中的子字典虽会被包装，但 `lock()` 的遍历没有继续进入容器。适配复杂嵌套配置时不要把“递归”理解成任意容器图的深度冻结。

## 9. 结果协议：用结构化多模态字典承接差异

Pipeline 的 `generate()` 原样返回 `runner.run_pipeline()` 的结果（`lightx2v/pipeline.py:482-489`）。常见结果不是单个 tensor，而是按模态命名的字典：

| 场景 | 结果示例 | 源码 |
|---|---|---|
| 标准视频 | `{"video": tensor_or_none}` | `lightx2v/models/runners/default_runner.py:523-577` |
| LTX2 音视频 | `{"video": ..., "audio": ...}` | `lightx2v/models/runners/ltx2/ltx2_runner.py:1086-1114` |
| 动作模型 | `{"actions": ...}` | `lightx2v/models/runners/wan/fastwam_runner.py:417-434` |
| 文本或图像 | `{"text": ...}` / `{"image": ...}` | `lightx2v/models/runners/hunyuan_image3/hunyuan_image3_runner.py:1490-1525` |
| 三维重建 | `{"output_dir": ..., "timings": ...}` | `lightx2v/models/runners/worldmirror/worldmirror_runner.py:654-655` |

`return_result_tensor=False` 时，许多 Runner 会把媒体保存到路径，并在对应模态键中返回 `None`。调用方应按 Runner 的结果契约消费，不能固定解包为“视频 tensor”。

当前返回键还没有完全归一，例如有的图像 Runner 使用 `image`，有的使用 `images`。服务端的规范化器目前明确读取 `images`（`lightx2v/server/services/inference/pipeline_image_encode.py:120-133`），这也是新增结构化结果时需要联动检查的边界。

## 10. 分布式：世界大小是 TP × CFG × SP

`set_parallel_config()` 读取：

- `tensor_p_size`：Tensor Parallel，切权重/计算；
- `cfg_p_size`：CFG 条件与无条件分支并行；
- `seq_p_size`：序列并行。

它首先验证：

```text
world_size = tensor_p_size × cfg_p_size × seq_p_size
```

不相等就直接报错（`lightx2v/utils/set_config.py:414-424`）。

当 TP > 1 时，设备网格按存在的维度建立，TP 是最内层：

```text
[cfg_p, seq_p, tensor_p]
```

否则保持 `[cfg_p, seq_p]` 二维网格（`lightx2v/utils/set_config.py:426-451`）。随后模型分别通过命名维度拿 group；例如 `BaseTransformerModel` 获取 `tensor_p` 和 `seq_p` group（`lightx2v/models/networks/base_model.py:85-111`）。

注意：网格能建立只说明拓扑合法，不代表某个模型支持这组策略。HunyuanImage3 有额外的 TP / CFG / SP、MoE、pipeline parallel 和 head 可整除约束（`lightx2v/utils/set_config.py:258-356`）；其他模型也可能在具体实现中拒绝 CPU Offload、缓存或某种组合。

## 12. 常见误区

### 误区 1：只要继承 DefaultRunner 就自动支持所有任务

`DefaultRunner.init_modules()` 只为一组明确任务绑定编码方法，未命中时不会自动生成实现（`lightx2v/models/runners/default_runner.py:124-139`）。更复杂的 Runner 可能自己分派任务。

### 误区 2：BaseRunner 的 `pass` 方法都是抽象方法

没有 `@abstractmethod` 就不会在实例化时强制检查。错误通常会在真实调用路径上更晚暴露。

### 误区 3：注册装饰器写了，任意入口就能查到

必须 import 定义该类的模块；还要通过入口自己的 choices 或参数校验。

### 误区 4：配置优先级永远只有“默认 < 模型 < 用户”

真实代码有两条 JSON 流和模型特例。应按 key 追踪写入时序，而不是背一句口号。

### 误区 5：配置锁能解决并发请求修改

它只拦截字典修改，没有同步、事务或请求隔离语义。服务按请求临时修改共享 Runner 配置时仍需要上层串行化或隔离。

### 误区 6：打开 enable_xxx 就代表模型支持

Pipeline 只负责收集配置；支持与组合约束由具体 Runner、Model、权重模块、Infer 和平台算子共同决定。

### 误区 7：所有输出都是视频

结果可能包含 image(s)、video、audio、text、actions 或 output_dir；保存模式下值还可能是 `None`。

## 14. 思考题

1. 为什么 `BaseRunner` 采用“部分空实现 + 生命周期包装”，而不是把所有能力都声明为抽象方法？这对非扩散模型有什么价值，又会带来什么晚失败风险？
2. 如果某 Runner 的 `init_modules()` 调用 `super().init_modules()`，为什么 `_init_modules_depth` 能避免 warmup 两次？如果内层初始化抛异常，warmup 会发生吗？
3. Pipeline 中增加了 Runner import，但忘记更新 CLI choices，会分别出现什么现象？反过来只更新 choices 又会怎样？
4. 为什么 Decoder 分离角色使用 `NullScheduler` 比到处写 `if scheduler is not None` 更容易维持通用清理协议？
5. 对一个同时返回视频、音频和动作的新模型，你会如何定义结构化结果，并检查哪些服务消费者？
6. 计划使用 16 张卡，配置 `tensor_p_size=2`、`cfg_p_size=2` 时，`seq_p_size` 应是多少？模型支持性还要到哪些层核验？
7. 为什么 `LockableDict` 的配置锁不等于并发控制？若服务允许并行请求且每请求调用 `set_config()`，应把隔离放在哪一层？
