## 1. 从 HTTP Body 到 GPU 推理的数据变换链

一个请求经过 5 次数据格式变换才到达推理引擎：

```
① HTTP JSON Body
   {"prompt": "a cat", "image_path": "http://...", "infer_steps": 20}
       │
       ▼ Pydantic 反序列化
② VideoTaskRequest（Pydantic Model）
   message.prompt = "a cat"
   message.image_path = "http://..."
   message.infer_steps = 20
   message.task_id = "auto-generated-uuid"
       │
       ▼ generate_with_stop_event() 提取字段
③ task_data（dict）
   {"prompt": "a cat", "image_path": "/cache/inputs/imgs/xxx.jpg",  ← URL 已下载
    "infer_steps": 20, "task_id": "...", "task": "i2v",
    "save_result_path": "/cache/outputs/xxx.mp4",
    "return_result_tensor": False/True, "seed": 42, ...}
       │
       ▼ worker.process_request()
       │  ├─ runner.set_config(task_data)      ← 更新 runner.config
       │  └─ update_input_info_from_dict()     ← 更新 input_info 字段
       │
④ runner.config（FrozenDict，临时解锁写入）
   config["infer_steps"] = 20
   config["save_result_path"] = "/cache/outputs/xxx.mp4"

⑤ input_info（dataclass 实例）
   input_info.prompt = "a cat"
   input_info.image_path = "/cache/inputs/imgs/xxx.jpg"
   input_info.seed = 42
   input_info.save_result_path = "/cache/outputs/xxx.mp4"
       │
       ▼ runner.run_pipeline(input_info)
   GPU 推理
```

**为什么需要 config 和 input_info 两个载体？**

| 维度 | `runner.config` | `input_info` |
|------|----------------|-------------|
| 持久性 | 模型加载时创建，常驻内存 | 每次请求前更新 |
| 内容 | 模型架构参数（dim, num_layers...）+ 运行时参数（infer_steps, target_height...） | 用户输入（prompt, image_path, seed...） |
| 消费者 | `model.__init__`、`scheduler.prepare`、`set_parallel_config` | `run_text_encoder`、`run_image_encoder`、`run_vae_encoder` |
| 线程安全 | FrozenDict + `temporarily_unlocked()` | 守护线程独占访问 |

## 2. `input_info` 的模板复用机制

**核心文件**：`lightx2v/utils/input_info.py`

### 2.1 InputInfo 的类型体系

框架为每种任务类型定义了一个 dataclass：

```python
@dataclass
class T2VInputInfo:         # 文生视频
    seed, prompt, negative_prompt, save_result_path,
    return_result_tensor, resize_mode, latent_shape, target_shape

@dataclass
class I2VInputInfo:         # 图生视频（比 T2V 多 image_path 等图像相关字段）
    seed, prompt, negative_prompt, image_path, save_result_path,
    return_result_tensor, resize_mode,
    original_shape, resized_shape, latent_shape, target_shape,
    pose, action_path

@dataclass
class T2AVInputInfo:        # 文生音视频（LTX2 等多模态）
    seed, prompt, negative_prompt, save_result_path,
    return_result_tensor, resize_mode, latent_shape, target_shape,
    audio_path, video_duration, talk_objects
```

### 2.2 模板创建与复用

```python
# worker.py:58 —— 初始化时创建一次
self.input_info = init_empty_input_info(args.task)
```

`init_empty_input_info("i2v")` 返回一个 `I2VInputInfo()` 实例，所有字段为默认值（空字符串/空列表）。这个实例在整个 Server 生命周期中**复用**，每次请求只更新有变化的字段：

```python
# input_info.py:458-461
def update_input_info_from_dict(input_info, data):
    for key in input_info.__dataclass_fields__:
        if key in data:
            setattr(input_info, key, data[key])
```

**为什么复用而不是每次新建？**

`input_info` 的 `latent_shape`、`original_shape` 等字段在 `run_input_encoder` 过程中被 Runner 写入（如 `self.input_info.latent_shape = latent_shape`）。如果每次新建，这些字段就需要由调用方预先计算，增加了 API 层的复杂度。复用实例让 Runner 自己负责填充计算结果字段。

### 2.3 多任务支持：动态合并 dataclass

如果服务需要同时支持多种任务类型（如 `support_tasks=["t2v", "i2v"]`），框架会**动态合并**多个 InputInfo 的字段：

```python
# input_info.py:338-363
```

## 3. `set_config()`：逐请求配置更新

**核心文件**：`lightx2v/models/runners/default_runner.py:167`

```python
def set_config(self, config_modify):
    logger.info(f"modify config: {config_modify}")
    with self.config.temporarily_unlocked():
        self.config.update(config_modify)
```

`self.config` 是 `FrozenDict`——初始化后默认不可修改（防止意外写入）。`temporarily_unlocked()` 是一个上下文管理器，临时允许修改，退出后重新冻结。

**哪些配置项会被逐请求修改？**

```python
# worker.py:84-94  process_request() 中注入的字段
task_data["task"] = self.runner.config["task"]       # 任务类型
task_data["return_result_tensor"] = bool(             # 是否在内存中返回结果 tensor
    task_data.get("return_result_tensor", False))     #   /sync 接口用 True，异步接口用 False
task_data["negative_prompt"] = task_data.get(...)     # 负面提示词

# 以下来自 HTTP 请求：
task_data["infer_steps"]           # 推理步数（可能每请求不同）
task_data["target_video_length"]   # 目标帧数
task_data["save_result_path"]      # 输出路径
task_data["seed"]                  # 随机种子
task_data["use_prompt_enhancer"]   # 是否使用提示词增强
```

**注意**：`config.update(config_modify)` 会把 `task_data` 中的所有 key 都写入 config，包括 `prompt`、`image_path` 等不属于 config 的字段。这些多余字段不会影响运行（config 是 dict，多余 key 无害），但也不会被 config 消费——它们由 `input_info` 承载。

```python
# base.py:35-46
async def _resolve_image_path(self, image_path: str) -> str:
    if not image_path:
        return ""

    if image_path.startswith("http"):
        # 格式 A：URL → 下载到 cache_dir/inputs/imgs/
```

### 4.2 Mask 对齐：`_pack_image_and_mask_as_dir()`

当用户同时提供 `image_path` 和 `image_mask_path` 时，Runner 期望它们打包成一个目录（`{base_name}.png` + `{base_name}_mask.png`）：

```python
# base.py:57-89
def _pack_image_and_mask_as_dir(self, task_data):
    image_file = Path(task_data["image_path"])
    mask_file = Path(task_data["image_mask_path"])

    # 创建临时目录
    image_pair_dir = self.file_service.input_image_dir / f"mask_pair_{uuid4().hex[:8]}"
    image_pair_dir.mkdir(parents=True, exist_ok=True)

    # 保存原图（转 RGB）
    base_name = image_file.stem or "image"
    with Image.open(image_file) as img:
        target_size = img.convert("RGB").size
        img.convert("RGB").save(image_pair_dir / f"{base_name}.png")

    # 保存 mask（对齐到原图分辨率）
    with Image.open(mask_file) as mask:
        mask_rgb = mask.convert("RGB")
        if mask_rgb.size != target_size:
            mask_rgb = mask_rgb.resize(target_size, Image.NEAREST)  # ← 最近邻插值保持边缘锐利
        mask_rgb.save(image_pair_dir / f"{base_name}_mask.png")

    # 用目录路径替换原始路径
    task_data["image_path"] = str(image_pair_dir)
    task_data["image_mask_path"] = ""   # 清空，Runner 从目录结构中识别 mask
```

**为什么用目录而不是两个独立路径？** 这是 Wan 的 VACE（Video Animation and Composition Editor）模式的约定——Runner 的 `read_image_input()` 会扫描目录，按 `*_mask.png` 命名规则自动识别 mask。

## 5. MediaHandler：统一的多媒体处理框架

**核心文件**：`lightx2v/server/media/base.py`、`image.py`、`audio.py`

框架用**模板方法模式**统一了图片和音频的 base64 检测与解码：

```
              MediaHandler (ABC)
              ├── get_media_signatures()    → Dict[bytes, str]  文件签名表
              ├── get_data_url_prefix()     → str               "data:image/" 或 "data:audio/"
              ├── get_data_url_pattern()    → str               正则表达式
              ├── get_default_extension()   → str               默认扩展名
              │
              ├── is_base64(data) ──────────→ 模板方法，子类可覆盖
              │     ├─ 检查 data URL 前缀
              │     └─ 解码前 100 字节，匹配文件签名
              │
              ├── extract_base64_data(data) → (base64_str, format_type)
              ├── detect_extension(data)    → str
              └── save_base64(data, dir)    → filepath
                    │
          ┌─────────┴─────────┐
          │                   │
    ImageHandler          AudioHandler
    ├── PNG/JPG/GIF/WEBP  ├── MP3/OGG/FLAC/WAV/M4A
    └── 单例模式           └── 单例模式
```

**base64 检测逻辑**：

```python
# base.py:33-48
def is_base64(self, data: str) -> bool:
    # 1. 检查 data URL 前缀（如 "data:image/png;base64,..."）
    if data.startswith(self.get_data_url_prefix()):
        return True

    # 2. 尝试解码前 100 字节，匹配文件签名
    try:
        if len(data) % 4 == 0:                        # base64 长度必须是 4 的倍数
            base64.b64decode(data, validate=True)      # 验证合法性
            decoded = base64.b64decode(data[:100])     # 解码前 100 字节
            for signature in self.get_media_signatures().keys():
                if decoded.startswith(signature):      # 匹配文件头
                    return True
    except:
        return False
```

**ImageHandler 的签名表**：

| 签名（bytes） | 格式 |
|-------------|------|
| `\x89PNG\r\n\x1a\n` | PNG |
| `\xff\xd8\xff` | JPEG |
| `GIF87a` / `GIF89a` | GIF |
| offset 8-12 = `WEBP` | WEBP（特殊检测） |

**AudioHandler 的签名表**：

| 签名（bytes） | 格式 |
|-------------|------|
| `ID3` / `\xff\xfb` / `\xff\xf3` / `\xff\xf2` | MP3 |
| `OggS` | OGG |
| `fLaC` | FLAC |
| `RIFF` + `WAVE` | WAV（特殊检测） |
| `ftyp` 等 | M4A（特殊检测） |

## 6. LoRA 的生命周期管理

**核心文件**：`lightx2v/server/services/inference/worker.py:126-165`

Server 支持**逐请求**切换 LoRA，无需重启服务。

### 6.1 状态转换图

```
  启动（无 LoRA）
       │
       │  请求 A: lora_name="style_v1.safetensors"
       ▼
  ┌─────────────────────────┐
  │ switch_lora("style_v1") │
  │  └─ _update_lora(path)  │
  │     current_lora = v1    │
  └───────────┬─────────────┘
              │
              │  请求 B: lora_name="style_v2.safetensors"  (换一个 LoRA)
              ▼
  ┌────────────────────────────┐
  │ switch_lora("style_v2")    │
  │  └─ _update_lora(path, s)  │  ← 直接覆盖，不需要先 remove
  │     current_lora = v2       │
  └───────────┬────────────────┘
              │

              ▼

  │     current_lora = None     │
  └───────────┬────────────────┘
              │
              │  请求 D: lora_name=None  (已无 LoRA，空操作)
              ▼
  ┌────────────────────────────┐
  │ current_lora already None  │
  │  → 跳过，不做任何操作       │
  └────────────────────────────┘
```

### 6.2 源码分析

```python
# worker.py:126-157
def switch_lora(self, lora_name: str, lora_strength: float):
    # 场景 1: 请求要求卸载 LoRA
    if lora_name is None:
        if self.current_lora_name is not None:    # 当前有 LoRA → 卸载
            self.runner.model._remove_lora()
            self.current_lora_name = None
        return                                     # 当前无 LoRA → 空操作

    # 场景 2: 请求的 LoRA 与当前相同 → 跳过
    current_strength = getattr(self, "current_lora_strength", None)
    if lora_name == self.current_lora_name and lora_strength == current_strength:
        return

    # 场景 3: 加载或切换 LoRA
    lora_path = self._lora_path(lora_name)   # lora_dir / lora_name
    if lora_path is None:
        logger.warning(f"LoRA file not found: {lora_name}")
        return

    self.runner.model._update_lora(lora_path, lora_strength)
    self.current_lora_name = lora_name
    self.current_lora_strength = lora_strength
```

**`_update_lora` 的底层**（`base_model.py:268`）：

```python
def _update_lora(self, lora_path, strength):
    lora_weight = self._load_lora_file(lora_path)  # safetensors → dict
    self.pre_weight.update_lora(lora_weight, strength)
    self.transformer_weights.update_lora(lora_weight, strength)
    self.post_weight.update_lora(lora_weight, strength)
```

**关键设计**：`_update_lora` 是**替换**语义（不是叠加）——新的 LoRA 权重直接覆盖旧的。不需要先 `_remove_lora` 再 `_update_lora`，单次调用即可完成切换。

## 7. `run_pipeline()`：推理主流程

**核心文件**：`lightx2v/models/runners/default_runner.py:483`

```python
@ProfilingContext4DebugL1("RUN pipeline", ...)  # ← Metrics 埋点
def run_pipeline(self, input_info):
    if GET_RECORDER_MODE():
        monitor_cli.lightx2v_worker_request_count.inc()  # 总请求计数器 +1

    self.input_info = input_info

    # 1. 提示词增强（如果配置了 use_prompt_enhancer=True）
    if self.config["use_prompt_enhancer"]:
        self.input_info.prompt_enhanced = self.post_prompt_enhancer()

    # 2. 输入编码（文本编码 + 图像编码 + VAE 编码）
    self.inputs = self.run_input_encoder()

    # 3. 去噪主循环 + VAE 解码 + 保存结果
    gen_video_final = self.run_main()

    if GET_RECORDER_MODE():
        monitor_cli.lightx2v_worker_request_success.inc()  # 成功计数器 +1
    return gen_video_final
```

### 7.1 `run_main()`：去噪循环与多段拼接

```python
# default_runner.py:366-410
def run_main(self):
    self.init_run()   # 准备 scheduler、设置 latent_shape 等

    for segment_idx in range(self.video_segment_num):
        self.check_stop()                        # ← 检查停止信号
        self.init_run_segment(segment_idx)        # 段初始化
        latents = self.run_segment(segment_idx)   # 去噪循环
        self.gen_video = self.run_vae_decoder(latents)  # VAE 解码
        self.end_run_segment(segment_idx)          # 拼接到 gen_video_final
```

### 7.2 `run_segment()`：逐步去噪

```python
# default_runner.py:175-208
def run_segment(self, segment_idx=0):
    infer_steps = self.model.scheduler.infer_steps

    for step_index in range(infer_steps):
        with ProfilingContext4DebugL1(
            "Run Dit every step",
            metrics_func=monitor_cli.lightx2v_run_per_step_dit_duration,
            metrics_labels=[step_index + 1, infer_steps],
        ):
            # 单段视频时，每步检查停止信号
            if self.video_segment_num == 1:
                self.check_stop()

            self.model.scheduler.step_pre(step_index=step_index)
            self.model.infer(self.inputs)          # ← DiT 前向推理
            self.model.scheduler.step_post()

            # 进度回调（如果设置了）
            if self.progress_callback:
                current_step = segment_idx * infer_steps + step_index + 1
                total = self.video_segment_num * infer_steps
                self.progress_callback((current_step / total) * 100, 100)

    return self.model.scheduler.latents
```

### 7.4 `pipeline_image_encode.py`：Tensor → PNG 内存编码

**核心文件**：`lightx2v/server/services/inference/pipeline_image_encode.py`

这个新模块负责将 `run_pipeline()` 的各种返回格式统一编码为 PNG bytes：

```python
def encode_pipeline_return_to_png_bytes(pipeline_return) -> Optional[bytes]:
    """将 run_pipeline 的返回值转换为 PNG 字节串"""
    # 1. 适配各种返回格式
    if isinstance(pipeline_return, tuple):      # BagelRunner: (images, audio)
        pipeline_return = pipeline_return[0]
    if isinstance(pipeline_return, dict):        # {"images": tensor} 或 {"video": tensor}
        images = pipeline_return.get("images")
        ...
    if isinstance(pipeline_return, torch.Tensor):
        return _tensor_to_png_bytes(pipeline_return)
    if isinstance(pipeline_return, Image.Image):
        return _pil_to_png_bytes(pipeline_return)
    if isinstance(pipeline_return, str):         # base64 字符串
        return _pil_to_png_bytes(Image.open(BytesIO(base64.b64decode(pipeline_return))))
```

**`_tensor_to_png_bytes` 的两条路径**：

```
输入: torch.Tensor [B, C, H, W] 或 [C, H, W] 或 [H, W, C]
       │
       ├─ .detach().cpu()                       GPU → CPU
       ├─ 自动检测 CHW / HWC 布局 → 统一为 CHW
       ├─ float [0,1] → uint8 [0,255] 转换
       │
       ├─ [快速路径] torchvision.io.encode_png 可用
       │    └── 直接从 CHW uint8 tensor 编码 PNG（无需 numpy/PIL 中转）
       │
       └─ [回退路径] torchvision 不可用
            └── CHW → HWC → numpy → PIL.Image → save(PNG)
```

**PNG 压缩级别**：通过环境变量 `LIGHTX2V_SYNC_PNG_COMPRESSION` 控制（默认 6，范围 0-9）。级别越高压缩率越大但编码越慢。

## 第五部分：同步推理接口

## 8. `/sync` 端点：等待完成并流式返回

**核心文件**：`lightx2v/server/api/tasks/image.py:90`

异步接口（`POST /v1/tasks/image/`）立即返回 `task_id`，客户端需轮询状态。同步接口（`POST /v1/tasks/image/sync`）会**阻塞直到推理完成**，然后直接返回结果文件。

```python
@router.post("/sync")
async def create_image_task_sync(
    request: Request,
    message: ImageTaskRequest,
    timeout_seconds: int = 600,        # 默认 10 分钟超时
    poll_interval_seconds: float = 0.5,
):
    task_id = task_manager.create_task(message)

    # 启动两个并发任务：等待结果 vs 检测断连
    wait_task = asyncio.create_task(
        _wait_task_and_stream_result(task_id, timeout_seconds, poll_interval_seconds)
    )
    disconnect_task = asyncio.create_task(
        _watch_client_disconnect(request, task_id)
    )

    # 等待任一完成
    done, pending = await asyncio.wait(
        {wait_task, disconnect_task},
        return_when=asyncio.FIRST_COMPLETED,
    )

    # 取消未完成的任务
    for p in pending:
        p.cancel()

    # 客户端断连 → 取消推理
    if disconnect_task in done and disconnect_task.result():
        raise HTTPException(status_code=499, detail="Client disconnected")

    return wait_task.result()   # StreamingResponse（文件流）
```

### 8.1 `_wait_task_and_stream_result`：轮询等待

```python
# image.py:22-53
async def _wait_task_and_stream_result(task_id, timeout_seconds, poll_interval_seconds):
    start_time = time.monotonic()
    while True:
        status = task_manager.get_task_status(task_id)

        if status == "completed":
            return _stream_file_response(full_path)  # ← 直接流式返回文件

        if status in ["failed", "cancelled"]:
            raise HTTPException(status_code=...)

        if (time.monotonic() - start_time) > timeout_seconds:
            task_manager.cancel_task(task_id)
            raise HTTPException(status_code=504, detail="Timeout")

        await asyncio.sleep(poll_interval_seconds)  # 非阻塞等待
```

### 8.2 `_watch_client_disconnect`：断连检测

```python
# image.py:56-62
async def _watch_client_disconnect(request: Request, task_id, poll_interval=0.2):
    while True:
        if await request.is_disconnected():   # Starlette 提供的检测方法
            task_manager.cancel_task(task_id)  # 客户端断开 → 取消任务
            return True
        await asyncio.sleep(poll_interval)
```

**设计亮点**：用 `asyncio.wait(FIRST_COMPLETED)` 实现"等待结果"和"检测断连"的竞赛。如果客户端在推理过程中关闭连接（如浏览器关闭），服务端能及时取消任务释放资源，而不是白白完成一个无人接收的推理。

```python
async def _download_with_retry(self, url, max_retries=3):
    retry_delay = 1.0              # 初始 1 秒
    max_retry_delay = 10.0         # 最大 10 秒

    for attempt in range(max_retries):
        try:
            response = await client.get(url)
            if response.status_code == 200:
                return response
            elif response.status_code >= 500:
                last_exception = ...   # 服务端错误 → 重试
            else:
                raise ...              # 客户端错误(4xx) → 不重试，直接抛出

        except (ConnectError, TimeoutException, NetworkError):
            last_exception = ...       # 网络错误 → 重试

        if attempt < max_retries - 1:
            await asyncio.sleep(retry_delay)
            retry_delay = min(retry_delay * 2, max_retry_delay)  # 指数退避
            # 1s → 2s → 4s（但不超过 10s）
```

### 10.1 Monitor 单例

```python
# monitor.py
class Monitor(MetricsClient):
    _instance = None
    _lock = threading.Lock()
    _initialized = False

    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            with cls._lock:
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
        return cls._instance

    def __init__(self, *args, **kwargs):
        if not self.__class__._initialized:
            super().__init__(*args, **kwargs)   # 初始化所有 Prometheus 指标
            self.__class__._initialized = True
```

使用方式：`from lightx2v.server.metrics.monitor import Monitor; monitor = Monitor()`，全局任何地方 `Monitor()` 都返回同一实例。

### 10.2 指标在推理流水线中的埋点位置

```
[API 层] HTTP 请求到达
 │
 │  monitor.lightx2v_api_request_total.inc(method, endpoint)   ← API 请求计数
 │  monitor.lightx2v_task_queue_pending_size.set(...)           ← 队列排队数（Gauge）
 │  monitor.lightx2v_task_queue_active_size.set(...)            ← 活跃任务数（Gauge）
 │  monitor.lightx2v_task_queue_capacity.set(...)               ← 队列容量（Gauge）
 │
 │  [请求完成]
 │  monitor.lightx2v_api_request_e2e_duration_seconds           ← API 端到端延迟
 │  [请求失败]
 │  monitor.lightx2v_api_request_error_total.inc(method, endpoint, error_type)
 │
 ▼
[推理层] run_pipeline()
 │
 │  monitor.lightx2v_worker_request_count.inc()     ← 总推理请求计数
 │
 ├── run_text_encoder()
 │     monitor.lightx2v_run_text_encode_duration     ← 文本编码耗时
 │       buckets: 1-30s（T5 编码通常 2-8 秒）
 │
 ├── run_image_encoder()
 │     monitor.lightx2v_run_img_encode_duration      ← 图像编码耗时
 │       buckets: 1-50ms（CLIP 编码很快）
 │
 ├── run_vae_encoder()
 │     monitor.lightx2v_run_vae_encoder_image_duration  ← VAE 编码图片耗时
 │       buckets: 60-120ms
 │     monitor.lightx2v_run_vae_encoder_pre_latent_duration  ← VAE 编码 latent 耗时
 │       buckets: 1-30s
 │
 ├── run_segment()
 │     for step in range(infer_steps):
 │       monitor.lightx2v_run_per_step_dit_duration  ← 每步 DiT 耗时
 │         labels: [step_no, total_steps]
 │         buckets: 30-900s
 │
 ├── run_vae_decoder()
 │     monitor.lightx2v_run_vae_decode_duration      ← VAE 解码耗时
 │       buckets: 1-30s
 │
 └── [完成]
      monitor.lightx2v_worker_request_success.inc()  ← 成功计数
      monitor.lightx2v_worker_request_duration        ← 总推理耗时

```

**新版新增的 API 层指标**（与推理层指标互补）：

| 指标名 | 类型 | 说明 |
|--------|------|------|
| `lightx2v_api_request_total` | Counter | API 请求总数（按 method, endpoint 分标签） |
| `lightx2v_api_request_error_total` | Counter | API 错误总数（按 method, endpoint, error_type） |
| `lightx2v_api_request_e2e_duration_seconds` | Histogram | API 端到端延迟（含排队等待时间） |
| `lightx2v_task_queue_pending_size` | Gauge | 当前排队任务数（实时值） |
| `lightx2v_task_queue_active_size` | Gauge | 当前活跃任务数（PENDING + PROCESSING） |
| `lightx2v_task_queue_capacity` | Gauge | 配置的队列容量上限 |

**API 层 vs 推理层指标的关系**：API 层的 `e2e_duration` 包含排队等待时间，而推理层的 `request_duration` 只计算推理本身。两者之差就是排队延迟。

### 10.3 Histogram 桶的设计思想

不同阶段的耗时范围差异巨大，框架为每个阶段设计了**定制化的桶分布**：

| 阶段 | 耗时范围 | 桶名称 | 桶分布特点 |
|------|---------|--------|-----------|
| 图像编码 | 1-50ms | `HYBRID_10_50MS_BUCKETS` | 1ms-50ms 密集，50ms-10s 稀疏 |
| VAE 编码 | 60-120ms | `HYBRID_60_120MS_BUCKETS` | 60-120ms 密集（5ms 间隔） |
| Init/End segment | 0.3-1.6s | `HYBRID_300MS_1600MS_BUCKETS` | 300ms-1.6s 密集（50ms 间隔） |
| 文本编码/VAE解码 | 1-30s | `HYBRID_1_30S_BUCKETS` | 1-10s 密集（0.5s 间隔） |
| DiT 单步 | 30-900s | `HYBRID_30_900S_BUCKETS` | 30-150s 密集（10s 间隔） |

**密集区间**设在该阶段最可能的耗时范围内，保证 P50/P90/P99 分位数的精度。

## 11. 错误处理与恢复

### 11.1 错误传播链

```
runner.run_pipeline() 抛出异常
  ↓
worker.process_request() 捕获
  → return {"status": "failed", "error": str(e)}
  ↓
inference_service.submit_task_async() 返回 error result
  → worker.processing = False（释放处理标志）
  ↓
generation_service.generate_with_stop_event() 检查 result
  → raise RuntimeError(error_msg)
  ↓
_process_single_task() 捕获
  → task_manager.fail_task(task_id, str(e))
  ↓
finally:
  → task_manager.release_processing_lock(task_id)
```

**关键设计**：无论推理成功还是失败，`_processing_lock` 都会在 `finally` 中释放。这保证了一个任务的失败不会阻塞后续任务——守护线程会继续处理队列中的下一个 PENDING 任务。

### 11.2 多卡场景的错误同步

```python
# worker.py:105-107
if self.world_size > 1:
    self.dist_manager.barrier()   # 所有 Rank 都执行到这里才继续
```

`barrier()` 确保所有 Rank 在推理结束后同步。如果 Rank 0 推理成功但 Rank 1 失败，`barrier()` 不会感知错误（它只是同步点）。错误只在 Rank 0 记录并返回给客户端。

### 11.3 Worker 循环的异常恢复

```python
# worker.py:167-190
async def worker_loop(self):
    while True:
        try:
            task_data = self.dist_manager.broadcast_task_data()
            if task_data is None:
                break
            await self.process_request(task_data)
        except Exception as e:
            # 连接断开 → 退出循环
            if "Connection closed" in str(e) or "Connection reset" in str(e):
                break
            # 其他错误 → 同步后继续循环
            logger.error(f"Rank {self.rank} worker loop error: {str(e)}")
            if self.world_size > 1 and task_data is not None:
                try:
                    self.dist_manager.barrier()
                except:
                    break    # barrier 也失败 → 退出
            continue         # 否则继续等待下一个任务
```

## 12. 思考题

1. **`update_input_info_from_dict` 只更新 `data` 中存在的字段。如果请求 A 设了 `image_path="/a.jpg"`，请求 B 没设 `image_path`，B 会用 A 的图片吗？**
   - 提示：`task_data` 是从 `message.model_fields_set` 提取的，没有设置的字段不在 dict 中

2. **`set_config(config_modify)` 会把 `prompt` 等字段写入 `runner.config`。这些多余字段会导致问题吗？**
   - 提示：config 是 dict，多余 key 无害，但 config 的内存会缓慢增长

3. **同步接口的 `_watch_client_disconnect` 以 0.2 秒间隔轮询。如果推理在 0.1 秒内完成，`disconnect_task` 还在 sleep 中，会有什么影响？**
   - 提示：`asyncio.wait(FIRST_COMPLETED)` 会取消 pending 的 task

4. **Mask 对齐使用 `Image.NEAREST` 插值。为什么不用 `BILINEAR`？**
   - 提示：mask 是二值/离散值图像，插值会产生中间值

5. **LoRA 的 `_update_lora` 是直接覆盖语义。如果用户想同时使用两个 LoRA（混合效果），当前架构能否支持？**
   - 提示：考虑 `lora_configs` 列表 vs 单个 `lora_name` 的差异
