## 1. 先看真实调用链

### 1.1 主流程

以下是时序图，不是 Python 伪代码：

```text
LightX2VPipeline.generate
  → runner.run_pipeline(input_info)
    → run_input_encoder()
      → run_text_encoder(...)
      → [按任务] run_image_encoder(...)
      → [按任务] run_vae_encoder(...)
      → 返回模型专属 inputs schema
    → run_main()
      → init_run()
        → scheduler.prepare(...)
      → 每个采样步
        → scheduler.step_pre(step_index)
        → model.infer(inputs)
          → pre_infer 读取 scheduler 状态和 inputs schema
          → transformer_infer
          → post_infer 写回预测结果
        → scheduler.step_post()
      → run_vae_decoder(...) 或 run_vae_decoder_stream(...)
```

源码锚点：

- `lightx2v/pipeline.py:433-488`：`generate()` 构造 `input_info`，调用 `runner.run_pipeline`。
- `lightx2v/models/runners/default_runner.py:630-645`：默认本地 `run_pipeline()` 先编码再运行主流程。
- `lightx2v/models/runners/default_runner.py:421-456`：`init_run()` 调 `prepare()`，`run_main()` 组织分段采样和 VAE 解码。
- `lightx2v/models/runners/default_runner.py:225-257`：默认采样循环固定为 `step_pre → model.infer → step_post`。
- `lightx2v/models/runners/wan/wan_runner.py:392-514`：Wan 还可以把 encoder、transformer、decoder 拆成远程服务角色。

### 1.2 “统一入口”不等于“统一返回值”

Runner 层常见外壳是：

```text
inputs
├── text_encoder_output
└── image_encoder_output
```

但这只统一了最外层容器。内层 key、张量形状和语义都由模型决定：

| 模型 | `text_encoder_output` 的关键字段 | 图像/条件字段 |
|---|---|---|
| Wan | `context`、可选 `context_null` | `clip_encoder_out`、`vae_encoder_out` |
| HunyuanVideo 1.5 | `context`、`context_null`、`byt5_features`、`byt5_masks` | `siglip_output`、`siglip_mask`、`cond_latents` |
| QwenImage | `prompt_embeds`、可选 `negative_prompt_embeds`；I2I 另含 `image_info` | I2I 为若干 `{"image_latents": ...}` |
| LTX2 | `v_context_p`、`a_context_p`、`v_context_n`、`a_context_n` | 条件通常进入 scheduler 的视频/音频 latent state，而不是统一的 CLIP 字段 |
| Z-Image | `prompt_embeds`、可选 `negative_prompt_embeds`；I2I 另含 `image_info` | I2I VAE latent 列表 |

对应源码：

- Wan schema：`lightx2v/models/runners/wan/wan_runner.py:528-563,845-852`。
- Wan 消费 schema：`lightx2v/models/networks/wan/infer/pre_infer.py:96-126`。
- HunyuanVideo 1.5 schema：`lightx2v/models/runners/hunyuan_video/hunyuan_video_15_runner.py:272-294,447-489`。
- QwenImage schema：`lightx2v/models/runners/qwen_image/qwen_image_runner.py:306-397`。
- LTX2 schema：`lightx2v/models/runners/ltx2/ltx2_runner.py:849-870`；消费位置在 `lightx2v/models/networks/ltx2/infer/pre_infer.py:67-74,162-164`。
- Z-Image schema：`lightx2v/models/runners/z_image/z_image_runner.py:118-128,191-213,250-258`。

**适配结论**：不要把“编码器输出”抽象成一个未经验证的 `context` tensor。新增模型时，schema 应由 Runner 的组装代码和 pre-infer 的读取代码共同定义，并在分布式传输、缓存和 warmup 中保持一致。

## 2. 当前模型与编码器矩阵

下表覆盖本课主线 Runner；仓库中其他派生模型仍应回到各自 Runner 核实。

| 模型/Runner | 文本编码器 | 独立图像语义编码器 | 像素/latent 编码器 | 关键事实 |
|---|---|---|---|---|
| Wan 2.1 / 2.2 | UMT5-XXL encoder | **OpenCLIP ViT-H/14 视觉塔** | `WanVAE` / `Wan2_2_VAE` | 视觉实现所在文件名虽叫 `xlm_roberta`，Wan I2V 实际取的是 OpenCLIP 的 ViT-H/14 visual tower |
| HunyuanVideo 1.5 | Qwen2.5-VL + ByT5 | SigLIP | `HunyuanVideo15VAE` | 文本输出同时携带 Qwen context 与 ByT5 features/masks |
| QwenImage | Qwen2.5-VL；可选 LightLLM kernel/service | 无独立图像塔 | `AutoencoderKLQwenImageVAE`；可切 TensorRT VAE | I2I 图像既参与 Qwen2.5-VL prompt 编码，也由 QwenImage VAE 产生 image latent |
| LTX2 | **Gemma 3** | 无独立图像塔 | **LTX2VideoVAE + LTX2AudioVAE** | 联合生成视频和音频，文本编码器分别输出 video/audio context |
| Z-Image | Qwen3 | 无独立图像塔 | `AutoencoderKLZImageVAE` | 当前 Qwen3 量化入口与 Wan T5/CLIP 不同 |

### 2.1 Wan：准确理解 OpenCLIP ViT-H/14

`CLIPModel` 构造 `clip_xlm_roberta_vit_h_14`，但 `run_image_encoder()` 调的是 `self.image_encoder.visual(...)`。视觉塔配置为：

- 输入分辨率 224；
- patch size 14，因此有 `16 × 16 = 256` 个 patch token；
- 加 1 个 class token，共 257 token；
- hidden width 1280；
- 视觉 Transformer 共 32 层；默认 `use_31_block=True` 时执行 `transformer[:-1]`，取第 31 个 block 后的 token features。

所以单图在 `CLIPModel.visual()` 返回时是 `[B,257,1280]`，Runner 的 `.squeeze(0)` 会把 batch 为 1 的结果变成 `[257,1280]`。若讨论接口形状，应先说明是在 encoder 边界还是 Runner 边界。

源码：

- 视觉塔定义和 token 形成：`lightx2v/models/input_encoders/hf/wan/xlm_roberta/model.py:242-347`。
- ViT-H/14 配置：`lightx2v/models/input_encoders/hf/wan/xlm_roberta/model.py:438-458`。
- Runner 加载与执行：`lightx2v/models/runners/wan/wan_runner.py:231-268,566-583`。
- Wan 14B 的层数来自配置；当前 Wan2.2 例子为 40 层：`configs/disagg/single_node/wan22_i2v_distill_controller.json:8`。

### 2.2 QwenImage：专用 VAE，可切 TensorRT

QwenImage 的基线并不是 HunyuanVideo VAE。Runner 明确导入并实例化 `AutoencoderKLQwenImageVAE`；其内部使用 Diffusers 的 `AutoencoderKLQwenImage`：

- `lightx2v/models/runners/qwen_image/qwen_image_runner.py:16,252-279`；
- `lightx2v/models/video_encoders/hf/qwen_image/vae.py:11-41`。

当 `vae_type="tensorrt"` 时，Runner 尝试构造 `TensorRTVAE`，不可用、引擎缺失或加载失败时回退 PyTorch VAE。TensorRT 实现支持 multi-profile 与按静态分辨率目录选择引擎，并在某个 encoder/decoder 引擎不可用时对该路径回退 `AutoencoderKLQwenImage`：

- Runner 路由与回退：`lightx2v/models/runners/qwen_image/qwen_image_runner.py:252-279`。
- TensorRT 初始化与 engine 发现：`lightx2v/models/video_encoders/trt/qwen_image/vae_trt.py:58-163`。
- TensorRT encode/decode 与 PyTorch fallback：`lightx2v/models/video_encoders/trt/qwen_image/vae_trt.py:208-238,319-394`。

这说明“VAE 可 TensorRT”是 QwenImage 当前实现的后端选择，不是所有 VAE 自动具备的能力。

### 2.3 LTX2：Gemma 3 + 视频 VAE + 音频 VAE

LTX2 文本路径加载 `Gemma3ForConditionalGeneration`，随后经过 feature extractor 和 embeddings processor，得到视频与音频两套 embedding。`GemmaEncoderOutput` 的字段是 `video_encoding`、`audio_encoding`、`attention_mask`：

- `lightx2v/models/input_encoders/hf/ltx2/gemma/encoders/base_encoder.py:13-65`。
- Gemma 3 加载：`lightx2v/models/input_encoders/hf/ltx2/model.py:101-145`。
- 正负 prompt 被展开成四个 context：`lightx2v/models/input_encoders/hf/ltx2/model.py:173-200`。

Runner 同时构造 `LTX2VideoVAE` 与 `LTX2AudioVAE`，分别处理视频 latent 和音频 latent：

- `lightx2v/models/runners/ltx2/ltx2_runner.py:277-333`。
- 视频/音频 latent shape：`lightx2v/models/runners/ltx2/ltx2_runner.py:335-368`。
- 联合解码：`lightx2v/models/runners/ltx2/ltx2_runner.py:873-904`。

因此把 LTX2 简化成“Gemma + 一个 VAE”会漏掉其联合音视频状态和两套解码链。

## 3. 编码器 Offload：三类实现，不是一套模板

### 3.1 类别一：整模型在调用边界迁移

典型做法是权重平时在 CPU，进入 `infer`/`visual`/`encode` 时迁到 `AI_DEVICE`，完成后迁回 CPU。例如 Wan CLIP：

```python
if self.cpu_offload:
    self.to_cuda()
...
if self.cpu_offload:
    self.to_cpu()
```

实际代码：`lightx2v/models/input_encoders/hf/wan/xlm_roberta/model.py:486-505`。

LTX2 Gemma 也在 `encode_text()` 外围迁移整个 `text_encoder`：`lightx2v/models/input_encoders/hf/ltx2/model.py:153-171`。VAE 也常采用类似边界，但具体类是否搬回、输出是否先转 CPU，应逐类检查。

### 3.2 类别二：Wan T5 单 GPU buffer 逐 block 搬运

Wan T5 的 `cpu_offload=True` 不是把整个 T5 一次搬入设备。它创建：

- 全部 block 的 CPU 侧权重容器；
- **一个** `offload_block_buffers` 设备槽；
- `t5_lazy_load=True` 时再创建**一个** CPU pinned 中转槽。

源码证据：

- 单设备槽与单 CPU 槽：`lightx2v/models/input_encoders/hf/wan/t5/model.py:57-76`，两个列表都由 `range(1)` 创建。
- T5 block 由 attention 与 FFN 两个 compute phase 组成：`lightx2v/models/input_encoders/hf/wan/t5/model.py:79-101`。
- 推理循环逐 block 把当前权重复制到 `cuda_buffers[0]` 后立即计算：`lightx2v/models/input_encoders/hf/wan/t5/model.py:580-612`。

它没有第二个 GPU 槽去覆盖“下一 block 传输”和“当前 block 计算”。因此不能把 DiT 的 block 双 buffer 模型直接套到 T5 上。

### 3.3 类别三：远程编码服务

QwenImage 的 `text_encoder_type="lightllm_service"` 会构造 `LightLLMServiceTextEncoder`，本进程只保留 tokenizer/processor 与客户端逻辑，hidden states 由 HTTP 服务返回；同机时还可走 shared memory：

- 路由：`lightx2v/models/runners/qwen_image/qwen_image_runner.py:68-76,221-247`。
- HTTP `/generate` 调用：`lightx2v/models/input_encoders/lightllm/qwen25_text_encoder_service.py:107-230`。
- shared memory 与 HTTP payload 回退：`lightx2v/models/input_encoders/lightllm/qwen25_text_encoder_service.py:288-349`。

这是“计算服务化”，与本地 CPU offload 不同：显存、故障重试、序列化、服务版本和输出 schema 都成为接口的一部分。

### 3.4 生命周期卸载不是第四种 block 算法

Runner 中大量条件是：

```python
if self.config.get("lazy_load", False) or self.config.get("unload_modules", False):
```

它表示在阶段或请求边界重新构造并删除 encoder/transformer/VAE 对象。例如 Wan 文本、图像和 VAE 路径见 `lightx2v/models/runners/wan/wan_runner.py:528-583,801-841`。这与编码器内部“整模型迁移”或“T5 逐 block 搬运”可以叠加，但概念不同。

## 4. `lazy_load`、`t5_lazy_load` 与 `unload_modules`

| 配置 | 当前作用域 | 关键效果 |
|---|---|---|
| `lazy_load` | 主要是 DiT/Runner 生命周期 | DiT 从按 block 拆分的 checkpoint 延迟读盘；Runner 在请求阶段重建并释放模块；默认 Runner 要求同时开启 `cpu_offload` |
| `t5_lazy_load` | Wan T5 内部 | 传给 `T5EncoderModel(..., lazy_load=...)`，使 T5 block 从自己的 checkpoint 按需读盘 |
| `unload_modules` | Runner 生命周期 | 即使不用 DiT 的按 block 读盘，也可在编码、DiT、VAE 阶段后删除模块实例以降低阶段间常驻内存 |

源码：

- `lazy_load` 初始化约束：`lightx2v/models/runners/default_runner.py:116-126`。
- Wan 单独读取 `t5_lazy_load`：`lightx2v/models/runners/wan/wan_runner.py:270-306`。
- T5 接收并使用该标志：`lightx2v/models/input_encoders/hf/wan/t5/model.py:796-842`。
- Runner 对 `lazy_load`/`unload_modules` 的请求级释放：`lightx2v/models/runners/default_runner.py:285-323,421-441,485-505`。

**重要约束**：开启 `lazy_load` 不会自动开启 `t5_lazy_load`。反过来，单独打开 `t5_lazy_load` 也只影响 Wan T5 的 block 权重读取，不会让 DiT 或其他编码器进入相同路径。

## 5. 量化路径为何不能假设全部共享

### 5.1 DiT 与编码器可能使用不同叶子实现

Wan DiT 的矩阵权重通常由 `MM_WEIGHT_REGISTER[dit_quant_scheme]` 选择叶子：`lightx2v/models/networks/wan/weights/transformer_weights.py:36-70`。

Wan T5 则有两条路径：

- 非 offload 路径使用 `q_linear.py` 中的量化 Linear 类；选择逻辑位于 `lightx2v/models/input_encoders/hf/wan/t5/model.py:197-234,285-319`。
- CPU offload 路径的 T5 block 用 `MM_WEIGHT_REGISTER` 构造可搬运叶子：`lightx2v/models/input_encoders/hf/wan/t5/model.py:103-144`。

Wan CLIP 同样在自己的 Attention/MLP 构造阶段选择专用量化 Linear：`lightx2v/models/input_encoders/hf/wan/xlm_roberta/model.py:63-99,152-191`。

其他例子：

- HunyuanVideo 1.5 的 Qwen2.5-VL 有自己的量化 scheme 分发：`lightx2v/models/input_encoders/hf/hunyuan15/qwen25/model.py:116-142`。
- QwenImage baseline Qwen2.5-VL 当前有独立的 INT4 入口：`lightx2v/models/input_encoders/hf/qwen25/qwen25_vlforconditionalgeneration.py:78-88`。
- Z-Image Qwen3 当前量化入口也单独限制为 INT4：`lightx2v/models/input_encoders/hf/z_image/qwen3_model.py:30-36`。
- LTX2 Gemma 3 当前由 Hugging Face 模型加载和可选 attention backend 负责，不等同于 Wan 的 T5 注册器路径：`lightx2v/models/input_encoders/hf/ltx2/model.py:101-110`。

### 5.2 新编码器量化适配时要逐项核对

1. checkpoint key 与量化 scale key；
2. 权重是否需要转置；
3. 激活量化位置和输出 dtype；
4. CPU offload 路径是否仍使用同一种叶子；
5. `AI_DEVICE` 后端是否注册了对应 kernel；
6. 不支持的组合是否在配置阶段明确拒绝；
7. 精度基线是否与未量化输出逐层对齐。

“DiT 已支持某 scheme”只能证明注册器中存在实现，不能证明某个 Hugging Face 编码器会自动使用它。

## 6. Scheduler 的真实基类与松散接口

### 6.1 `BaseScheduler` 的实际字段

基线中的 `BaseScheduler` 位于 `lightx2v/models/schedulers/scheduler.py:10-31`，初始化字段为：

| 字段 | 含义 |
|---|---|
| `config` | 模型配置 |
| `generator` | 随机数生成器，初始为 `None` |
| `latents` | 当前 latent 状态 |
| `step_index` | 当前采样步 |
| `infer_steps` | 推理步数 |
| `caching_records` | 每步 feature-caching 记录，初始全 `True` |
| `flag_df` | 调度/缓存相关标志 |
| `transformer_infer` | 可选的 transformer infer 反向引用 |
| `infer_condition` | CFG 当前分支 |
| `keep_latents_dtype_in_scheduler` | 是否阻止基类在敏感 dtype 场景下转换 latent |

`noise_pred`、`timesteps`、`sigmas` 等不是基类统一初始化的字段，由具体 scheduler 自己添加。Wan 在 `lightx2v/models/schedulers/wan/scheduler.py:12-30` 添加了这些状态。

### 6.2 `NullScheduler`

`NullScheduler` 只有 `clear()`，用于不运行 DiT 的拆分式角色，例如 decode 服务：

- 定义：`lightx2v/models/schedulers/scheduler.py:4-8`。
- 选择：`lightx2v/models/runners/base_runner.py:212-217`。

因此不能假设任意 Runner 的 `scheduler` 都有 `prepare`、`latents` 或 `step_post`。

### 6.3 prepare-step 只是 Runner 与具体模型之间的松散约定

常见约定是：

- `prepare(...)`：初始化随机状态、条件 latent、sigma/timestep；
- `step_pre(step_index, ...)`：把当前步状态整理成模型输入；
- `step_post(...)`：用模型预测更新状态。

但签名并不统一：

| Scheduler | `prepare` / `step_pre` 例子 |
|---|---|
| Wan | `prepare(seed, latent_shape, image_encoder_output=None)` |
| QwenImage | `prepare(input_info)` |
| LTX2 | `prepare(seed, video_latent_shape, audio_latent_shape, ...多个条件参数)` |
| HunyuanVideo SR | `prepare(seed, latent_shape, lq_latents, upsampler, image_encoder_output=None)` |
| Wan self-forcing | `step_pre(seg_index, step_index, is_rerun=False)` |
| Wan audio AR | `step_pre(segment_idx, step_index, xt)`、`step_post(xt)` |

源码索引：`lightx2v/models/schedulers/wan/scheduler.py:84-106`、`lightx2v/models/schedulers/qwen_image/scheduler.py:664-736`、`lightx2v/models/schedulers/ltx2/scheduler.py:373-422`、`lightx2v/models/schedulers/hunyuan_video/scheduler.py:152-177`、`lightx2v/models/schedulers/wan/self_forcing/scheduler.py:98`、`lightx2v/models/schedulers/wan/audio/scheduler.py:230-238`。

**适配结论**：不要只继承 `BaseScheduler` 就期待某个通用 Runner 自动调用成功。要同时核对目标 Runner 的调用点、模型读取/写回的字段、clear/reset 语义和多阶段重入。

## 7. Wan 同样是 Flow Matching：UniPC 与 Euler 是求解器差异

### 7.1 不要被 `noise_pred` 变量名误导

Wan 代码把模型输出保存在 `noise_pred`，但其更新关系是 Flow Matching 的线性路径语义。若

\[
x_\sigma=(1-\sigma)x_0+\sigma\epsilon,\qquad v=\epsilon-x_0,
\]

则

\[
x_0=x_\sigma-\sigma v.
\]

Wan 的 `convert_model_output()` 正是：

```python
sigma_t = self.sigmas[self.step_index]
x0_pred = sample - sigma_t * model_output
```

源码：`lightx2v/models/schedulers/wan/scheduler.py:159-178`。

因此这里的模型输出应按 flow/velocity 语义理解；`noise_pred` 是历史命名，不足以证明 prediction type 是 epsilon。

### 7.2 Wan：Flow Matching + UniPC 多步求解

WanScheduler：

1. 建立 sigma/timestep 序列：`lightx2v/models/schedulers/wan/scheduler.py:84-106,130-157`；
2. 把 flow 输出转成 `x0_pred`：`159-178`；
3. 保存历史 `model_outputs`、`timestep_list`、`last_sample`；
4. 使用 UniPC predictor/corrector 更新：`195-381`；
5. 在 `step_post()` 中完成历史滚动和下一状态计算：`389-430`。

UniPC 的关键是使用多个采样点的信息构造更高阶更新，而不是改变模型训练目标。

### 7.3 HunyuanVideo 1.5：Flow Matching + Euler

HunyuanVideo 1.5 使用线性 sigma schedule，经可选 shift 后，直接做一阶 Euler：

```python
dt = self.sigmas[self.step_index + 1] - self.sigmas[self.step_index]
self.latents = sample + model_output * dt
```

源码：`lightx2v/models/schedulers/hunyuan_video/scheduler.py:74-88,140-144`。

### 7.4 正确比较

| 维度 | WanScheduler | HunyuanVideo15Scheduler |
|---|---|---|
| 生成路径语义 | Flow Matching | Flow Matching |
| 求解器 | UniPC predictor-corrector，多步 | Euler，一阶单步 |
| 历史状态 | `model_outputs`、`timestep_list`、`last_sample` | 无多步历史 |
| 模型输出使用 | 先转成 `x0_pred` 供 UniPC 公式使用 | 作为向量场直接乘 `dt` |
| 代码复杂度来源 | 高阶多步公式和 warmup order | 一阶积分 |

不能从“使用 UniPC”推出模型是 epsilon diffusion，也不能从“使用 Euler”推出模型一定更差；求解误差取决于向量场、步长分布、训练校准和任务。

## 8. `shift`：是时间参数化，不是固定经验区间

Wan 的变换为：

\[
f_s(\sigma)=\frac{s\sigma}{1+(s-1)\sigma}.
\]

源码：`lightx2v/models/schedulers/wan/scheduler.py:96,139-145`。HunyuanVideo 1.5 使用同形公式：`lightx2v/models/schedulers/hunyuan_video/scheduler.py:77-91`。

正确理解：

- `s=1` 时不改变 sigma；
- 对 `0<σ<1`，`s>1` 会把采样点映射到更高的 sigma，令轨迹在下降过程中更久停留在高 sigma 区域；`0<s<1` 则相反；
- 它改变的是离散采样点在时间/噪声坐标上的分布，不是“直接提高细节”的独立开关；
- 最佳值与模型训练、分辨率、token 数、蒸馏方式和具体 scheduler 有关；
- LTX2 还会根据 token anchor 计算 shift：`lightx2v/models/schedulers/ltx2/scheduler.py:771-824`；QwenImage 可根据 image sequence length 计算 `mu`：`lightx2v/models/schedulers/qwen_image/scheduler.py:20-36,640-661`。

所以教程不应给出脱离模型配置与验证集的固定“正确范围”。适配时应先复现官方 schedule，再做同 seed、同输入、同 prediction type 的质量回归。

## 9. Wan 条件 latent：初始化后还要逐步覆盖

### 9.1 适用模型与任务

WanScheduler 的 `_uses_conditioned_latent_prefix()` 当前要求：

- `task ∈ {i2v, s2v, rs2v}`；
- `model_cls ∈ {wan2.2, wan2.2_matrix_game3}`。

源码：`lightx2v/models/schedulers/wan/scheduler.py:70-82`。

### 9.2 两次覆盖缺一不可

第一次在初始噪声生成后：

\[
x=(1-m)\odot x_{cond}+m\odot x_{noise}.
\]

见 `lightx2v/models/schedulers/wan/scheduler.py:108-126`。

第二次在每次 UniPC 更新后：

\[
x_{next}\leftarrow(1-m)\odot x_{cond}+m\odot x_{next}.
\]

见 `lightx2v/models/schedulers/wan/scheduler.py:389-430`。这一步保证固定前缀不会被数值求解器逐步改写。

Matrix-Game-3 的官方 adapter 也在自己的 `step_post()` 中重新混合条件 latent：`lightx2v/models/runners/wan/wan_matrix_game3_runner.py:943-1004`。其 Runner 在开始采样后释放输入字典中的原始 `vae_encoder_out`，因为 scheduler 已持有条件引用：`lightx2v/models/runners/wan/wan_matrix_game3_runner.py:1619-1625`。普通 Wan2.2 对应释放点是 `lightx2v/models/runners/default_runner.py:435-442`。

### 9.3 与 DiT concat 条件不要混淆

Wan pre-infer 还会读取 `image_encoder_output["vae_encoder_out"]`，并在非空时与当前 latent 沿 channel 维拼接后 patchify：`lightx2v/models/networks/wan/infer/pre_infer.py:107-126`。这是给 DiT 的条件输入；scheduler 的固定前缀覆盖则约束被更新的 latent 状态。两者可能使用同一来源，但职责不同。

## 10. VAE 与流式解码的真实位置

### 10.1 Runner 层负责选择普通或流式路径

`DefaultRunner.run_main()` 在每个 segment 去噪后检查 `use_stream_vae`：

- 普通路径调用 `run_vae_decoder(latents)`；
- 流式路径遍历 `run_vae_decoder_stream(latents)`，最后沿时间维拼接。

源码：`lightx2v/models/runners/default_runner.py:447-456,494-505`。

### 10.2 WanVAE 内部按 latent 时间步产出结果

- 内部 decoder 的 `decode_stream()` 逐个 latent 时间位置调用带 feature cache 的 decoder 并 `yield`：`lightx2v/models/video_encoders/hf/wan/vae.py:740-758`。
- `WanVAE.decode_stream()` 处理并行/非并行分支、CPU offload 和输出裁剪：`lightx2v/models/video_encoders/hf/wan/vae.py:1614-1633`。

所以流式逻辑不只在 Runner 里“切 tensor”；真正保证时序卷积上下文的是 VAE decoder 的 `_feat_map`/`_conv_idx` cache。适配新 VAE 时，只有类实现了相容的 `decode_stream` 语义，Runner 的开关才成立。

LTX2 视频 VAE 的 decode 本身返回 iterator，Runner 会消费这些 chunk：`lightx2v/models/video_encoders/hf/ltx2/model.py:104-119`、`lightx2v/models/runners/ltx2/ltx2_runner.py:882-904`。不要假设所有 VAE 都使用 Wan 的 cache 结构。

## 12. 常见误区

1. **把 Wan 图像编码器称为 XLM-Roberta 图像模型。** 文件包含多模态 CLIP 命名，但 I2V 实际调用 OpenCLIP ViT-H/14 视觉塔。
2. **把 Wan CLIP 输出写成 `[257,4096]`。** 当前视觉塔 hidden width 是 1280；`[B,257,1280]` 才是 encoder 边界形状。
3. **认为所有编码器输出都是 `context/context_null`。** QwenImage、LTX2、HunyuanVideo 1.5 的 schema 都不同。
4. **认为 QwenImage 使用 HunyuanVideo VAE。** 当前基线是 `AutoencoderKLQwenImageVAE`，并可由 TensorRT backend 替换。
5. **把 LTX2 写成“Gemma + 视频 VAE”。** 它是 Gemma 3 + 视频 VAE + 音频 VAE，并联合维护两种 latent state。
6. **认为 Wan T5 block offload有两个 GPU copy 槽。** 当前实现只有一个设备槽，逐 block 覆盖使用。
7. **认为编码器量化全部复用 DiT 注册器。** 多个编码器仍有专用 q_linear、HF/INT4 或其他路径。
8. **把 `lazy_load`、`t5_lazy_load`、`unload_modules` 当同一个开关。** 三者作用域和 checkpoint 读取方式不同。
9. **把 BaseScheduler 当成严格抽象接口。** 它没有抽象方法约束，具体 scheduler 的方法签名和字段并不统一。
10. **根据变量名 `noise_pred` 判断 Wan 预测 epsilon。** 应以 `convert_model_output` 和官方训练参数化为准。
11. **把 Wan 与 HunyuanVideo 的差别说成“扩散对 Flow Matching”。** 两者都走 Flow Matching，核心差别之一是 UniPC 与 Euler 求解器。
12. **认为 shift 越大就固定地越有细节。** shift 是时间重参数化，效果必须结合模型和 schedule 验证。
13. **只在初始时写入条件帧。** Wan2.2/MG3 固定前缀还要在每个 step 后覆盖。
14. **把 DDIM 当成换一个类名即可。** 必须先匹配模型 prediction type、训练 alpha/sigma 参数化和 Runner 字段契约。

## 13. 思考题

1. Wan 的变量叫 `noise_pred`，但 `x0_pred = sample - sigma * model_output`。请从线性 flow 路径推导为什么这里的 `model_output` 可解释为 velocity。
2. 为什么 WanScheduler 在 `prepare_latents()` 和 `step_post()` 都要混合 `vae_encoder_out`？只保留第一次会发生什么？
3. `CLIPModel.visual()` 返回 `[B,257,1280]`，为什么 WanRunner 常见输出却是 `[257,1280]`？FLF2V 又如何处理两张图？
4. 如果给 QwenImage 的远程 LightLLM encoder 增加缓存，cache key 至少应覆盖哪些 prompt、图像处理和模型版本信息？
5. 新模型官方使用 DDIM 时，应先确认哪些 prediction type 和 schedule 信息？若模型训练为 flow velocity，为什么不能直接套用 epsilon 形式的 DDIM 更新式？
6. 比较 `lazy_load=True,t5_lazy_load=False` 与 `lazy_load=False,t5_lazy_load=True`：DiT、Wan T5 和 Runner 生命周期分别会怎样变化？
7. LTX2 的正负 prompt 为什么要产出四个 context，而不是 Wan 式的两个 context？请从视频/音频联合去噪路径回答。
8. 设计一个 scheduler 接口一致性测试：至少覆盖 `prepare` 后字段、首步 `step_pre`、末步 `step_post`、`clear` 和固定条件 latent 不变量。

### DDIM 设计题边界

DDIM 在本课只能作为设计练习。开始实现前必须先回答：

- checkpoint 预测的是 epsilon、velocity、sample 还是 flow field？
- 训练使用的 alpha/sigma 定义是什么？
- 是否存在从当前 prediction type 到 DDIM 所需参数化的严格变换？
- timestep spacing、终点处理和 stochasticity 参数是否与官方实现一致？

没有这些信息时，写出一个形式上有 `prepare/step_pre/step_post` 的类并不代表采样正确。
