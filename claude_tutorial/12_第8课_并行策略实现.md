## 前置知识：什么是 `DeviceMesh`

在进入 LightX2V 的并行实现之前，先补一下 PyTorch `DeviceMesh` 的基本概念——本课所有并行配置都建立在它之上。

### A. 朴素做法的痛点：`new_group` 散落各处

在 `DeviceMesh` 之前，PyTorch 多维并行的写法是手动调用 `torch.distributed.new_group(ranks=[...])` 建子通信组。例如 8 卡做 `(cfg=2, seq=4)` 二维并行：

```python
# 老写法：自己算 rank 列表，手动建组
cfg_groups = [dist.new_group([0,4]), dist.new_group([1,5]),
              dist.new_group([2,6]), dist.new_group([3,7])]
seq_groups = [dist.new_group([0,1,2,3]), dist.new_group([4,5,6,7])]

# 业务代码里还要根据当前 rank 找到自己属于哪一组
my_cfg_group = cfg_groups[dist.get_rank() % 4]
my_seq_group = seq_groups[dist.get_rank() // 4]
```

问题：rank 编号映射散落代码各处、容易写错；扩展到 3D（加个 PP）时组数爆炸；不同模块各自 `new_group` 可能造成状态不一致。

### B. `DeviceMesh`：把 N 维 rank 拓扑显式建模

`DeviceMesh` 把所有 rank 排成一个 N 维"网格"，每一维起一个名字。一次构造，所有维度的子通信组都自动派生：

```python
from torch.distributed.tensor.device_mesh import init_device_mesh

# 8 卡组成 (2, 4) 的二维网格
mesh = init_device_mesh("cuda", (2, 4), mesh_dim_names=("cfg_p", "seq_p"))
```

mesh 的 rank 排布（按行优先）：

```
            seq_p=0  seq_p=1  seq_p=2  seq_p=3
cfg_p=0     rank 0   rank 1   rank 2   rank 3
cfg_p=1     rank 4   rank 5   rank 6   rank 7
```

拿子通信组只需一行：

```python
cfg_group = mesh.get_group(mesh_dim="cfg_p")  # 沿 cfg_p 维度（即列）
seq_group = mesh.get_group(mesh_dim="seq_p")  # 沿 seq_p 维度（即行）
```

- 当前 rank=2（处于 `cfg_p=0, seq_p=2`），那么：
  - 它的 `cfg_group` 自动是 `[2, 6]`（与同列的 rank 6 通信，做 cond/uncond all_gather）。
  - 它的 `seq_group` 自动是 `[0, 1, 2, 3]`（与同行的 rank 0/1/3 通信，做序列并行 a2a）。

**关键收益**：rank 映射不再手算，写代码只需说"我要在哪个维度上通信"。

### C. 一维 mesh

如果只用一种并行（比如纯 TP），就是一维 mesh：

```python
mesh = init_device_mesh("cuda", (8,), mesh_dim_names=("tensor_p",))
tp_group = mesh.get_group(mesh_dim="tensor_p")  # 全部 8 卡
```

这正是 LightX2V 的 TP 路径（见 `set_config.py:209`）。

### D. 在 mesh 上拿 rank：全局 vs 子组

```python
dist.get_rank()                 # 全局 rank（0~7）
dist.get_rank(seq_group)        # 在 seq_p 子组里的 rank（0~3）
dist.get_world_size(seq_group)  # seq_p 子组大小（4）
```

LightX2V 的代码大量使用"子组 rank"——例如 `_seq_parallel_pre_process` 用 `dist.get_rank(self.seq_p_group)` 决定切分到哪一片，这跟全局 rank 是不一样的概念。

### E. 为什么 LightX2V 用 mesh 不用 `new_group`

回到 `set_parallel_config`（下一节会详细看），它用了：

```python
config["device_mesh"] = init_device_mesh(AI_DEVICE, (cfg_p_size, seq_p_size),
                                         mesh_dim_names=("cfg_p", "seq_p"))
```

后续 `wan/model.py`、`transformer_infer.py`、`ulysses_attn.py` 全部通过 `config["device_mesh"].get_group(mesh_dim="seq_p" / "cfg_p")` 拿组。**整个工程只有一处建 mesh 的地方**，避免了散落 `new_group` 带来的状态混乱。这也是为什么三个并行开关（`tensor_parallel`/`seq_parallel`/`cfg_parallel`）的初始化都收敛到同一个函数。

### F. 一句话总结

> `DeviceMesh` = 一个 N 维 rank 网格 + 每维一个名字，让你按"维度名"取通信组，而不是按"rank 列表"建组。

带着这个心智模型继续往下读，`mesh_dim="seq_p"`、`mesh_dim="cfg_p"` 这种写法就不会陌生。

## 第一部分：并行配置入口

### 1. `set_parallel_config`：单一入口

**核心文件**：`lightx2v/utils/set_config.py:202`

LightX2V 把所有并行相关的初始化收敛到一个函数 `set_parallel_config`，逻辑非常简洁——根据 `config["parallel"]` 字典里给定的维度大小，构建一维或二维 `DeviceMesh` 并打开对应的开关：

```@/data/wengzicheng/LightX2V_tutorial/LightX2V/lightx2v/utils/set_config.py:202-229
 def set_parallel_config(config):
     if config["parallel"]:
         tensor_p_size = config["parallel"].get("tensor_p_size", 1)

         if tensor_p_size > 1:
             # Tensor parallel only: 1D mesh
             assert tensor_p_size == dist.get_world_size(), f"tensor_p_size ({tensor_p_size}) must be equal to world_size ({dist.get_world_size()})"
             config["device_mesh"] = init_device_mesh(AI_DEVICE, (tensor_p_size,), mesh_dim_names=("tensor_p",))
             config["tensor_parallel"] = True
             config["seq_parallel"] = False
             config["cfg_parallel"] = False
         else:
             # Original 2D mesh for cfg_p and seq_p
             cfg_p_size = config["parallel"].get("cfg_p_size", 1)
             seq_p_size = config["parallel"].get("seq_p_size", 1)
             assert cfg_p_size * seq_p_size == dist.get_world_size(), f"cfg_p_size ({cfg_p_size}) * seq_p_size ({seq_p_size}) must be equal to world_size ({dist.get_world_size()})"
             config["device_mesh"] = init_device_mesh(AI_DEVICE, (cfg_p_size, seq_p_size), mesh_dim_names=("cfg_p", "seq_p"))
             config["tensor_parallel"] = False

             if config["parallel"] and config["parallel"].get("seq_p_size", False) and config["parallel"]["seq_p_size"] > 1:
                 config["seq_parallel"] = True

             if config.get("enable_cfg", False) and config["parallel"] and config["parallel"].get("cfg_p_size", False) and config["parallel"]["cfg_p_size"] > 1:
                 config["cfg_parallel"] = True

         # warmup dist
         _a = torch.zeros([1]).to(f"{AI_DEVICE}:{dist.get_rank()}")
         dist.all_reduce(_a)
```

**关键设计**：

1. **二选一的两条分支**：Tensor 并行单独走 1D mesh，CFG/序列并行共用 2D mesh `(cfg_p, seq_p)`。这意味着 **TP 与 CFG/SP 当前是互斥的**——这是出于 DiT 推理场景（无 MoE、单卡能装下权重的常见情况）下的工程取舍。

2. **`device_mesh` 是唯一通信组的来源**：后续所有需要 `seq_p_group` 或 `cfg_p_group` 的代码，统一通过 `config["device_mesh"].get_group(mesh_dim="seq_p")` 拿到子通信组，避免散落多处 `new_group` 带来的状态混乱。

3. **三个开关位 `tensor_parallel/seq_parallel/cfg_parallel`** 是模型层 `if` 分支的判断依据。把"维度是否启用"展平为布尔值，好处是模型代码不必反复解析嵌套字典。

4. **warmup all_reduce**：最后那个看似多余的 1 元素 all_reduce 是为了**强制 NCCL 完成首轮拓扑探测**，避免第一次真正推理时把建链时间算进端到端延迟。下一小节专门展开这件事。

### 1.5 NCCL 建链流程（warmup 在做什么）

代码里 `dist.all_reduce(_a)` 看起来只是加了个 1 元素张量，但它背后触发的是 NCCL 的**完整初始化链路**。如果不 warmup，第一次真正的 attention all_to_all 会突然慢几百毫秒到几秒——那就是把建链时间算进了端到端延迟。

#### A. PyTorch 启动 NCCL 之前：先有 TCPStore

`torchrun` / `init_process_group` 启动时，会先在 rank 0 拉起一个 **TCPStore**（基于 `MASTER_ADDR:MASTER_PORT` 的 KV 服务）。所有 rank 通过 TCPStore 交换"我是谁、我在哪"等元信息——这是用 TCP/IP 的，不走 GPU。

```
rank 0 ──┐
rank 1 ──┼──► TCPStore (MASTER_ADDR:MASTER_PORT)   ← 仅用于交换元信息
rank N ──┘
```

#### B. 第一次集合通信触发 NCCL 通信器创建

NCCL 的 `ncclComm_t`（通信器）是**懒创建**的：直到第一次真正调用集合通信（`all_reduce` / `all_gather` / `all_to_all` ...）时，PyTorch 才会调用 `ncclCommInitRank`。这时发生四件事：

1. **生成 unique_id**：rank 0 调用 `ncclGetUniqueId()` 生成一个 128 字节的随机 ID。
2. **通过 TCPStore 广播 unique_id**：其他 rank 从 TCPStore 拉到这个 ID。
3. **bootstrap 全互联**：所有 rank 用 unique_id 建立一张临时的 TCP 全连接网（"bootstrap network"），交换各自的 GPU PCI 信息、NIC 信息、IP 等。
4. **拓扑探测 + 算法选择**：NCCL 扫描每张卡的 NVLink/PCIe/IB/RoCE 拓扑，构建 ring/tree/CollNet 的传输路径。

#### C. 真正的数据通道：NVLink / IB / RoCE / SHM

拓扑探测完成后，NCCL 为每对需要通信的 rank 选一条**最佳通道**：

| 物理位置 | 通道 |
|---------|------|
| 同一张卡内 | （不通信） |
| 同主机、同 NVSwitch | **NVLink**（最快，~600 GB/s） |
| 同主机、跨 PCIe root | **PCIe P2P** 或 **共享内存（SHM）** |
| 跨主机、有 IB/RoCE | **GPUDirect RDMA**（不走 CPU） |
| 跨主机、只有以太网 | **TCP/IP socket** |

这一步会在每张卡上分配 **NCCL 内部 buffer**（默认每个通信器几十 MB）、注册 IB MR、建好 QP——和第 7 课讲的 RDMA 建链是同一套流程，只是被 NCCL 封装了。

#### D. ring/tree 算法的"环"是什么

NCCL 默认对 `all_reduce` 用 **Ring AllReduce**：所有 rank 排成一个环，先做 reduce-scatter（环上转一圈累加），再做 all-gather（环上再转一圈广播）。`init_device_mesh` 的 mesh 维度信息会被 NCCL 用来选环的方向——**这就是 mesh 维度名最终会落到通信路径上的原因**。

对 `all_to_all`（Ulysses 用），算法不一样（pairwise 或 brucks），但建链阶段一致。

#### E. 为什么必须 warmup

把上面所有事情串起来，第一次集合通信要做：

```
TCPStore 交换 unique_id ──► bootstrap TCP 全互联 ──►
拓扑探测（扫 NVLink/PCIe/IB） ──► 选算法/选通道 ──►
分配 NCCL buffer ──► 建 IB QP / NVLink 连接 ──►
真正的 all_reduce
```

实测耗时从几百毫秒（单机 8 卡）到几秒（跨节点 IB），且**只有第一次**才付。LightX2V 在 `set_parallel_config` 末尾用 1 元素 all_reduce 把这一切提前触发完，于是第一帧推理的 latency 就只剩"实际数据 all_reduce"的成本——这对扩散模型尤其重要，因为第一步去噪本来就是用户感知到的"首响"。

#### F. 何时建链会失败

了解流程后也就知道常见报错对应哪一步：

| 报错 | 卡在哪一步 |
|------|-----------|
| `Connection refused / TCPStore timeout` | A 步：MASTER_ADDR/PORT 不通 |
| `NCCL WARN Bootstrap : no socket interface found` | C 步：NIC 没识别，需要设 `NCCL_SOCKET_IFNAME` |
| `ibv_open_device failed` / `IB transport failed` | C 步：IB/RoCE 网卡不可用，需要 `NCCL_IB_DISABLE=1` 退化到 TCP |
| `unhandled cuda error` 在第一次 a2a | C/D 步：拓扑探测拿到错的 PCIe 信息 |

这些 NCCL_* 环境变量都是在 warmup 这次 all_reduce 时**第一次被读**，所以调试并行问题先看 warmup 阶段日志（`NCCL_DEBUG=INFO`），比看真正业务代码有效得多。

#### G. 一句话总结

> NCCL 建链 = TCPStore 交换 unique_id → bootstrap 全互联 → 拓扑探测 → 选通道（NVLink/IB/...）→ 建 buffer/QP。一次性、懒触发，warmup 把它从"首帧推理"里挪出来。

## 第二部分：CFG 并行——双路前向的天然并行

### 3. CFG 是什么

Classifier-Free Guidance（CFG）几乎是所有扩散模型推理必备：每一步去噪需要分别跑一次 **conditional**（带 prompt）和 **unconditional**（空 prompt）前向，再线性组合：

```
noise_pred_guided = noise_pred_uncond + scale * (noise_pred_cond - noise_pred_uncond)
```

两次前向**完全独立**——不共享中间激活、不交换权重，只在最后一步合并结果。这就是 CFG 并行的天然机会：把两次前向放到 2 张卡上同时算，理论加速 ~2×。

### 4. 实现：rank 决定算 cond 还是 uncond

**核心文件**：`lightx2v/models/networks/wan/model.py:168`

```@/data/wengzicheng/LightX2V_tutorial/LightX2V/lightx2v/models/networks/wan/model.py:168-193
         if self.config["enable_cfg"]:
             if self.config["cfg_parallel"]:
                 # ==================== CFG Parallel Processing ====================
                 cfg_p_group = self.config["device_mesh"].get_group(mesh_dim="cfg_p")
                 assert dist.get_world_size(cfg_p_group) == 2, "cfg_p_world_size must be equal to 2"
                 cfg_p_rank = dist.get_rank(cfg_p_group)

                 if cfg_p_rank == 0:
                     noise_pred = self._infer_cond_uncond(inputs, infer_condition=True)
                 else:
                     noise_pred = self._infer_cond_uncond(inputs, infer_condition=False)

                 noise_pred_list = [torch.zeros_like(noise_pred) for _ in range(2)]
                 dist.all_gather(noise_pred_list, noise_pred, group=cfg_p_group)
                 noise_pred_cond = noise_pred_list[0]  # cfg_p_rank == 0
                 noise_pred_uncond = noise_pred_list[1]  # cfg_p_rank == 1
             else:
                 # ==================== CFG Processing ====================
                 noise_pred_cond = self._infer_cond_uncond(inputs, infer_condition=True)
                 noise_pred_uncond = self._infer_cond_uncond(inputs, infer_condition=False)

             noise_pred_guided = noise_pred_uncond + self.scheduler.sample_guide_scale * (noise_pred_cond - noise_pred_uncond)
```

**要点**：

1. **`cfg_p_size == 2` 是硬约束**——CFG 只有两路前向，没有 4 路扩展空间。
2. **通信只在每个 step 末尾发生一次 all_gather**：每张卡只跑自己那一路的整个 transformer，结束后把 `noise_pred` 张量（潜空间大小，远小于权重）交换一次。通信占比极低，几乎线性加速。
3. **没有显存收益**：每张卡仍持有完整模型，CFG 并行换的是**时间**不是**显存**。
4. **与 seq 并行天然组合**：每张 cfg_p_rank 卡内部还可以再叠 seq_p 子组，参见下面 §8。

### 5. 何时选 CFG 并行

- 单卡显存够装模型 → 拿 2 卡做 CFG，**最简单、加速比最高**。
- 推理使用场景 `enable_cfg=True`（蒸馏后的少步模型如 4-step CFG-distilled 模型可能 `enable_cfg=False`，这时 CFG 并行无效）。
- 4 卡以上 → 通常 `cfg_p_size=2` 之外再叠 seq 并行，组成二维 mesh。

## 第三部分：序列并行（Ulysses）——长序列推理的关键

### 6. 为什么需要序列并行

视频扩散的视觉 token 数会随分辨率/帧数爆炸：

- 720p / 81 帧 / Wan 模型，patchify 后 `seq_len ≈ 75600`。
- Self-Attention 的 QK^T 显存正比于 `seq_len^2`，单卡 attention 直接 OOM。
- TP 切 hidden 维度对 attention 的 `seq_len^2` 矩阵无能为力。

**序列并行**的思路：让 N 张卡各自只持有 `seq_len / N` 的 token 切片，把"长序列在单卡 attention"变成"短序列在每卡 attention"，但需要在 attention 内部做一次维度重排（seq → head），保证每张卡看到的还是完整的 KV 序列。这就是 **Ulysses** 算法。

### 7. Ulysses 的核心：seq ↔ head All-to-All

**核心文件**：`lightx2v/common/ops/attn/utils/all2all.py`

```@/data/wengzicheng/LightX2V_tutorial/LightX2V/lightx2v/common/ops/attn/utils/all2all.py:7-44
 def all2all_seq2head(input, group=None):
     assert input.dim() == 3, f"input must be 3D tensor"
     world_size = dist.get_world_size(group=group)
     shard_seq_len, heads, hidden_dims = input.shape
     seq_len = shard_seq_len * world_size
     shard_heads = heads // world_size
     input_t = (
         input.reshape(shard_seq_len, world_size, shard_heads, hidden_dims)
         .transpose(0, 1)
         .contiguous()
     )
     output = torch.empty_like(input_t)
     dist.all_to_all_single(output, input_t, group=group)
     output = output.reshape(seq_len, shard_heads, hidden_dims).contiguous()
     return output
```

**Ulysses 的数据流（每个 attention 层）**：

```
进 attention 之前       :  [seq/N, heads,   d]   ← seq 切分
─ all2all_seq2head ──► :  [seq,   heads/N, d]   ← 切到 head 维
执行 local attention   :  [seq,   heads/N, d]   ← 完整 seq、部分 heads
─ all2all_head2seq ──► :  [seq/N, heads,   d]   ← 切回 seq 维
出 attention 之后       :  [seq/N, heads,   d]
```

每个 attention 调用内部需要 **2 次 All-to-All**。其余层（LayerNorm、FFN、modulation）都是 token-wise 操作，本来就支持 seq 切分，**零通信**即可完成。

### 7.1 `all2all_seq2head` 源码逐行精讲

这一节把上面 17 行代码完全拆开，理解 reshape/transpose 的每一次维度变化、`all_to_all_single` 在内存里到底搬了什么。

#### 起点：每张卡手里的张量

进入 attention 之前，每张卡只有 `seq_len / N` 行 token，但拿着**全部 heads**：

```
input.shape = (shard_seq_len, heads, hidden_dims)
            =       (S/N,        H,       D)
```

举个具体例子：4 卡 SP，`seq_len=8, heads=4, D=2`。每张卡是 `(2, 4, 2)`：

```
rank 0: tokens [0,1]  × heads [h0,h1,h2,h3]
rank 1: tokens [2,3]  × heads [h0,h1,h2,h3]
rank 2: tokens [4,5]  × heads [h0,h1,h2,h3]
rank 3: tokens [6,7]  × heads [h0,h1,h2,h3]
```

目标是变成"每张卡持有完整 8 个 token，但只有 1 个 head"，这样 attention 的 `QK^T` 才能算完整。

#### 第 1 步：reshape 把 heads 维度切成 N 份

```python
input.reshape(shard_seq_len, world_size, shard_heads, hidden_dims)
#               (S/N,            N,          H/N,         D)
```

- `world_size = N = 4`，`shard_heads = H/N = 1`
- 形状从 `(2, 4, 2)` 变成 `(2, 4, 1, 2)`
- **物理内存没动，只是把"heads=4"重新解读为"world_size=4 × shard_heads=1"**

语义上：`[s, w, h, d]` 中 `w` 这一维代表"这部分 head 应该送到第 w 个 rank"。例如 rank 0 上的张量第 `w=2` 那一片，是要发给 rank 2 的（rank 2 最终要持有 head h2）。

#### 第 2 步：`transpose(0, 1)` —— a2a 的关键一步

```python
.transpose(0, 1)  # (S/N, N, H/N, D) → (N, S/N, H/N, D)
```

- 形状变成 `(4, 2, 1, 2)`
- 内存不连续，所以紧跟 `.contiguous()` 触发一次拷贝重排

**为什么必须把 `world_size` 转到第 0 维？**

`dist.all_to_all_single` 的语义是：把输入张量沿**第 0 维**等分成 `world_size` 块，第 `i` 块发给 rank `i`；同时收到 `world_size` 块拼回输出张量的第 0 维。也就是说 a2a 的"分发单位"永远是 dim=0。

所以我们必须先把"该发给谁"那一维（`w`）放到 dim=0：

```
转置前 (S/N, N, H/N, D)：       第 0 维是 token，没法直接发
转置后 (N,   S/N, H/N, D)：     第 0 维是目标 rank，正好喂给 a2a
```

`.contiguous()` 保证 `[w=0 的全部数据 | w=1 的全部数据 | ...]` 在物理内存里连续排列——a2a 底层是按字节切的，没这一步会发错数据。

#### 第 3 步：`all_to_all_single` 在做什么

```python
output = torch.empty_like(input_t)            # (N, S/N, H/N, D)
dist.all_to_all_single(output, input_t, group=group)
```

直观图（4 卡，每张卡的 input_t shape = `(N, S/N, H/N, D)`）：

```
通信前：
rank 0: [(给r0的块) (给r1的块) (给r2的块) (给r3的块)]
rank 1: [(给r0的块) (给r1的块) (给r2的块) (给r3的块)]
rank 2: [(给r0的块) (给r1的块) (给r2的块) (给r3的块)]
rank 3: [(给r0的块) (给r1的块) (给r2的块) (给r3的块)]

       ─── all_to_all_single ───►

通信后：
rank 0: [(r0给的块) (r1给的块) (r2给的块) (r3给的块)]   ← 现在拥有所有 token，但只有 head h0
rank 1: [(r0给的块) (r1给的块) (r2给的块) (r3给的块)]   ← 只有 head h1
rank 2: [(r0给的块) (r1给的块) (r2给的块) (r3给的块)]   ← 只有 head h2
rank 3: [(r0给的块) (r1给的块) (r2给的块) (r3给的块)]   ← 只有 head h3
```

形象说：**a2a 相当于一次跨 rank 的"矩阵转置"**——把 `[rank, slot]` 的二维拓扑转置成 `[slot, rank]`。每张卡发出的"第 i 块"和接收的"第 i 块"都是和 rank i 之间的点对点通信，N 张卡共发出 N×(N−1) 条消息，但 NCCL 会内部用 ring 或 pairwise 算法折叠成 O(N) 步。

通信量分析：每张卡发 `S/N × H/N × D × N = S × H/N × D` 字节出去（也收同样多）。

#### 第 4 步：reshape 回 3D 张量

```python
output = output.reshape(seq_len, shard_heads, hidden_dims).contiguous()
#                       (S,       H/N,         D)
```

- 通信后形状是 `(N, S/N, H/N, D) = (4, 2, 1, 2)`
- reshape 时，前两维 `N × S/N = S = 8` 自动合并成完整序列维度

**关键问题：合并后 token 顺序对吗？**

`output[w, s, h, d]` 在通信后语义是"来自 rank w 的第 s 个 token 的第 h 个 head"。reshape 把 `(w, s)` 按 C-order 展平成 `w * S/N + s`：

```
new index 0 = (w=0, s=0) = rank0 的 token 0 = 全局 token 0  ✓
new index 1 = (w=0, s=1) = rank0 的 token 1 = 全局 token 1  ✓
new index 2 = (w=1, s=0) = rank1 的 token 0 = 全局 token 2  ✓
new index 3 = (w=1, s=1) = rank1 的 token 1 = 全局 token 3  ✓
...
new index 7 = (w=3, s=1) = rank3 的 token 1 = 全局 token 7  ✓
```

刚好对上原始全局顺序——这正是 §8 中 `_seq_parallel_pre_process` 用 `torch.chunk(x, world_size, dim=0)[cur_rank]` 切分的逆操作。**前面那次 transpose+contiguous 看似是多余的内存拷贝，但它正是让 reshape 后顺序自动正确的关键**。

#### 第 5 步：`@dynamo.disable` 的作用

```python
@dynamo.disable
def all2all_seq2head(input, group=None):
```

`torch.compile` 默认会把函数 trace 成 FX graph，但 a2a 这种集合通信涉及多 rank 同步，trace 后的图可能在不同 rank 上不一致（比如某些 rank 上 reshape 被融合掉），导致死锁。`@dynamo.disable` 强制保留 eager 执行，避免 compile 介入通信代码。

#### 第 6 步：`all2all_head2seq` 是逆操作

attention 算完后要切回去，`all2all_head2seq` 就是 `seq2head` 的反向：

```
attention 输出: (S, H/N, D)
   reshape  → (N, S/N, H/N, D)
   transpose(1, 2) + reshape → (N, H/N, S/N, D)   ← 把 head 维度提前
   all_to_all_single                              ← 同 a2a
   reshape (H, S/N, D) → transpose(0, 1) → (S/N, H, D)
```

注意它比 `seq2head` 多一次 transpose——因为这次要"按 head 分发"，需要把 head 维度放到 a2a 的 dim=0；最后还得再转回 `(seq, heads, ...)` 的常规顺序。两次 transpose 让接口对外保持 `(seq, heads, hidden)` 的标准约定，调用方完全无感。

#### 第 7 步：维度变化全图

```
                              ┌── reshape ──► (S/N, N, H/N, D)
                              │
进 attention: (S/N, H, D) ────┼── transpose(0,1).contiguous() ──► (N, S/N, H/N, D)
                              │
                              └── all_to_all_single ──► (N, S/N, H/N, D)（语义变了）
                                                              │
                                                              ▼
                                                        reshape ──► (S, H/N, D)
                                                              │
                                                              ▼
                                                       做 local attention
                                                              │
                                                              ▼
                                                  ─── all2all_head2seq ───
                                                              │
                                                              ▼
出 attention: (S/N, H, D)
```

两端形状对称是设计上的故意——上下游模块完全不需要知道里面发生过 a2a。

#### 第 8 步：约束与陷阱

| 检查项 | 原因 |
|--------|------|
| `heads % world_size == 0` | 第 1 步 reshape 要把 H 切成 N 份，整除才合法。GQA 头数小（如 2、4）时 8 卡 Ulysses 直接挂掉 |
| `shard_seq_len` 必须相等 | a2a 要求每个 rank 发送等量数据；这就是为什么 `_seq_parallel_pre_process` 要 padding 到 `world_size * f` 倍数 |
| 输入 `.contiguous()` | reshape 不改变内存，但 transpose 后必须 contiguous，否则 a2a 拿到错的字节 |
| dtype 一致 | a2a 是按字节搬运，所有 rank 的 dtype 必须一致；FP8 通信路径会先全员量化再 a2a |
| 不要在 compile 区调用 | `@dynamo.disable` 已经保护了，但调用方如果再用 `torch.compile` 包一层，仍可能踩坑 |

理解到这一层，再看 `ulysses_attn.py` 里 q/k/v 各做一次 `seq2head`、attention 后做一次 `head2seq`，整个 Ulysses 的数据流就完全打通了。

#### 第 9 步：为什么不能通过 padding heads 绕过 `heads % N == 0`

很自然的一个想法："padding 序列就能绕过 seq 整除约束，那 padding heads 不也能绕过 head 整除约束吗？" 看起来对称，但实际不行——padding heads 的代价大得多，而且会破坏多个语义。下面分四点说明。

##### (1) Heads 是模型权重的固定属性，不是动态形状

seq 维度是**激活**的形状，每帧、每分辨率都不一样，padding 几行 token 不影响权重——`F.pad` 一下就走人。

heads 维度是**模型架构**的一部分：

```
W_q.shape = (hidden, heads * head_dim)
W_k.shape = (hidden, kv_heads * head_dim)
W_o.shape = (heads * head_dim, hidden)
```

要 padding 一个"假 head"，必须同时给 `W_q / W_k / W_v / W_o` 都加上对应的零行/零列。这不是一次 `F.pad`，是**改权重**——意味着每次启动加载 checkpoint 都要重新切片拼接，且要保证零行的 `W_q` 出来的 Q 真的是 0、零列的 `W_o` 真的把假 head 的输出 mask 掉。这个改造跨多个权重模块，工程代价远大于 seq padding。

##### (2) GQA / MQA：Q 头数 ≠ KV 头数，padding 会破坏分组语义

现代模型（Llama-3、Mistral、Wan2.2）几乎都是 **Grouped-Query Attention**：

```
heads (Q) = 12
kv_heads  = 4    ← 每 3 个 Q head 共享 1 组 K/V
```

如果想让 8 卡 Ulysses 工作，按朴素 padding：

- Q 头要 padding 到 16（`heads // 8 = 2`），加 4 个假 Q head
- KV 头只有 4，padding 到 8 才整除 → 加 4 个假 KV head
- 但 GQA 的"分组关系"是 `q_head_i 用 kv_head_{i // 3}`，新加的假 Q head（index 12~15）该映射到哪个 KV head？没有合法答案。

要么**重新设计分组表**（破坏模型语义），要么 **把 GQA 退化成 MHA**（额外复制 KV 8 倍，显存暴涨）。两条路都不可接受。

##### (3) 假 heads 会浪费算力 + 浪费通信带宽

假设 `heads=12, world_size=8`，padding 到 16：

- 每张卡 attention 计算量 ∝ `heads/N × seq² = 2 × seq²`，**比单卡完整 12 头少了 33%**——但其中 4 个 head 是假的，真正有效计算只有 `1 × seq² × 8 = 8 × seq²`，不如不并行（单卡 `12 × seq²`）。
- a2a 通信量 ∝ `heads/N × seq × hidden`，假 heads 也要传输——25% 通信带宽白费。

**Ulysses 的核心收益假设是"head 切完每张卡都在做有效计算"**，padding heads 把这个假设打破了。

##### (4) FlashAttention 不支持"输出 mask 掉某些 head"

就算你愿意付出上面的代价，最后一步还是过不去：FlashAttention 的 forward kernel 没有"忽略某些 head"的开关。要么 attention 计算后再用一段额外代码把假 head 的 output 抹零（再做一次 `gather`），要么放弃 flash 改用普通 SDPA——前者引入额外通信和 kernel 启动，后者直接 OOM（FlashAttention 本来就是 Ulysses 长序列方案的前提）。

##### 对比：seq padding 为什么能接受

回头看 `_seq_parallel_pre_process` 里的 seq padding：

```python
padding_size = (multiple - (x.shape[0] % multiple)) % multiple
if padding_size > 0:
    x = F.pad(x, (0, 0, 0, padding_size))
```

- 不改权重，只 pad 激活
- padding 行参与 attention 是无害的（注意力分数会算到这些零行上，但因为 V 也是零，输出贡献是零；而且后处理 `_seq_parallel_post_process` 会切回原长度）
- 对计算量的浪费比例 = `padding_size / total_seq`，扩散模型 seq≈75600 时 padding 几行接近 0%

**两者根本区别：seq 是"可以 pad 到对齐的样本维"，heads 是"固定的架构维"**。

##### 那 head 数不整除时实际怎么办

LightX2V 的工程答案是 **§11 提到的"换 Ring Attention"**：

```json
"parallel": {
    "seq_p_size": 8,
    "seq_p_attn_type": "ring"
}
```

Ring 沿 seq 维度切，根本不动 head——天然不需要整除约束。8 卡 + GQA(kv_heads=4) 也能跑。这正是 LightX2V 同时维护两套序列并行算子的根本理由。

### 9. 为什么文本 token "不切分"

Wan / Hunyuan 这类视频 DiT 把 image token + text token 拼成一个长序列做 self-attention。但二者性质很不同：

| 维度 | image token | text token |
|------|-------------|-----------|
| 数量 | 数万 ~ 十万 | 几百（Wan: text_len=512） |
| 是否切分 | **切** —— 是 SP 主要收益来源 | **不切** —— 数量小，切了不省事还增加复杂度 |
| All-to-All 参与 | 参与（重排到 head 维度） | 直接广播给所有 rank |

`UlyssesAttnWeight.apply` 内部的 `img_qkv_len` / `txt_qkv_len` 切分（见 `ulysses_attn.py:70-86`）就是为了把这两段分别处理：image 段进 All-to-All，text 段以"完整副本"形式拼到每张卡上，参与 attention 计算。

`UlyssesAttnWeight.apply` 接受三个开关：

### 11. Ring Attention 替代

`seq_p_attn_type: "ring"` 切到 `ring_attn.py`：另一种序列并行算法，避免 All-to-All，改用环状 P2P 传 KV。两者 trade-off 不同：

- **Ulysses**：通信量小（只重排），但要求 `heads % world_size == 0`，对 GQA 头数少的模型不友好。
- **Ring**：通信量大（每步要传完整 KV 块），但对 head 数无限制，且能把通信与计算重叠。

LightX2V 把它们放在同一注册器键 `seq_p_attn_type` 下，模型层完全不感知细节差异。

### 11.1 Ring Attention 详解

Ring 与 Ulysses 思路完全不同：**Q 不动，K/V 在 N 张卡之间像传纸条一样转一圈，每张卡每收到一块就和自己手里的 Q 算一次局部 attention，最后把 N 次局部结果用 LSE（log-sum-exp）合并成全局 softmax 结果**。这样既不要求 `heads % N == 0`，也能让"传 KV"和"算 attention"在时间上重叠。

#### A. 数据布局：Q 不动，KV 接力传

每张卡一开始持有同样的切片：

```
rank 0:  Q[0:S/N]   K[0:S/N]   V[0:S/N]   ← 自己的 token
rank 1:  Q[S/N:2S/N] K[S/N:2S/N] V[S/N:2S/N]
...
rank N-1: Q[(N-1)S/N:S] K[(N-1)S/N:S] V[(N-1)S/N:S]
```

每张卡要算 attention(Q_local, K_global, V_global)，但 K/V 散在 N 张卡上。Ring 的做法是让 K/V **沿环传 N−1 次**，每张卡每接收一份外来 KV 就算一次"局部 attention"。

#### B. 环形 P2P 通信：`RingComm`

**核心文件**：`lightx2v/common/ops/attn/utils/ring_comm.py`

```@/data/wengzicheng/LightX2V_tutorial/LightX2V/lightx2v/common/ops/attn/utils/ring_comm.py:7-46
 class RingComm:
     def __init__(self, process_group: dist.ProcessGroup = None):
         self._process_group = process_group
         self._ops = []
         self.rank = dist.get_rank(self._process_group)
         self.world_size = dist.get_world_size(self._process_group)
         self._reqs = None

         self.send_rank = (self.rank + 1) % self.world_size
         self.recv_rank = (self.rank - 1) % self.world_size

         if process_group is not None:
             self.send_rank = dist.get_global_rank(self._process_group, self.send_rank)
             self.recv_rank = dist.get_global_rank(self._process_group, self.recv_rank)

     def send_recv(self, to_send: torch.Tensor, recv_tensor=None):
         ...
         send_op = dist.P2POp(dist.isend, to_send, self.send_rank, group=self._process_group)
         recv_op = dist.P2POp(dist.irecv, res, self.recv_rank, group=self._process_group)
         self._ops.append(send_op)
         self._ops.append(recv_op)
         return res

     def commit(self):
         self._reqs = dist.batch_isend_irecv(self._ops)

     def wait(self):
         for req in self._reqs: req.wait()
```

**几个关键点**：

1. **`send_rank = (rank+1) % N`、`recv_rank = (rank-1) % N`** —— 单向环，每张卡只跟左右邻居通信。N 卡只有 N 条 P2P 连接（vs Ulysses 全连接 N×(N−1)/2）。
2. **`isend/irecv` 异步**：发送和接收都是非阻塞的，挂入 `_ops` 队列后用 `batch_isend_irecv` 一次性提交。返回的 `req` 直到 `wait()` 才同步——这就是"通信与计算重叠"的接口。
3. **`commit / wait` 两阶段**：调用方在 commit 之后可以**接着算 attention**，等真正用到下一份 KV 时才 `wait()`。

#### C. 主循环：N 步流水线

回到 `ring_attn.py:132-176`，骨架是：

```python

        RING_COMM.commit()                        # 启动通信，立刻返回

    # 2. 用当前手里的 (q, k, v) 算一块局部 attention（与通信重叠！）
    block_out, block_lse = self.ring_attn_sub(q, k, v)

    # 3. 把这一块的结果用 LSE 合并到全局 out
    out, lse = self.update_out_and_lse(out, lse, block_out, block_lse)

    if step + 1 != world_size:
        RING_COMM.wait()                          # 等通信完，切到下一份 KV
        k, v = next_k, next_v
```

直观时序图（4 卡）：

```
step 0:  rank 0 用 KV[0]   rank 1 用 KV[1]   rank 2 用 KV[2]   rank 3 用 KV[3]
         同时:  KV[0]→r1   KV[1]→r2   KV[2]→r3   KV[3]→r0
step 1:  rank 0 用 KV[3]   rank 1 用 KV[0]   rank 2 用 KV[1]   rank 3 用 KV[2]
         同时:  KV[3]→r1   ...
step 2:  rank 0 用 KV[2]   rank 1 用 KV[3]   ...
step 3:  rank 0 用 KV[1]   rank 1 用 KV[2]   ...   ← 最后一步不再传
```

走完 N 步，每张卡都用过了所有 N 份 KV，等价于完整 attention。

#### D. LSE 合并：在线 softmax

每一步只算了"Q 对一块 K/V"的 attention（softmax 分母不完整）。要把 N 个局部结果合成正确的全局 softmax，必须用 **log-sum-exp 在线更新**：

```@/data/wengzicheng/LightX2V_tutorial/LightX2V/lightx2v/common/ops/attn/ring_attn.py:29-45
 @torch.jit.script
 def _update_out_and_lse(out, lse, block_out, block_lse):
     block_out = block_out.to(torch.float32)
     block_lse = block_lse.transpose(-2, -1).unsqueeze(dim=-1)
     # new_lse = lse + log(1 + exp(block_lse - lse))
     # exp(lse - new_lse) * out + exp(block_lse - new_lse) * block_out
     out = out - F.sigmoid(block_lse - lse) * (out - block_out)
     lse = lse - F.logsigmoid(lse - block_lse)
     return out, lse
```

这是 FlashAttention 同款数学：`flash_attn_interface._flash_attn_forward` 同时返回 `out` 和 `lse`（log-sum-exp of softmax），ring 拿到每一步的 `(block_out, block_lse)` 后用上面公式增量合并。**正是因为 FlashAttention 暴露了 LSE，Ring Attention 才能做到与单卡 attention 数值完全等价**。

数学上等价于：

```
softmax(QK^T) V  =  Σ_i softmax_i * V_i
                 =  按 LSE 合并所有 (block_out_i, block_lse_i)
```

#### E. 图文 token 怎么处理

Ring 也有图文分离逻辑（`ring_attn.py:111-153`）：

- **image K/V**：参与 ring 传递（每步发给下一个 rank）。
- **text K/V**：**不参与传递**——所有 rank 在最后一步把本地 text KV 拼回 `(k, v)` 后再算一次 attention。和 Ulysses 的"text 不切"思路一致。
- 此外 Wan 的 `txt_mask_len` 用 padding 区分有效/无效 text token，最后用一段独立的 `flash_attn_varlen_func` 处理 mask 段（`ring_attn.py:180-196`）。

#### F. 通信与计算重叠

这是 Ring 相对 Ulysses 的**核心优势**：

```
时间 ──►
rank i:  [算 attention 块 0]   [算 块 1]   [算 块 2]   [算 块 3]
                ↕通信↕         ↕通信↕      ↕通信↕
         发 KV0 / 收 KVx   发 KV3 / 收 KVy   ...
```

只要 attention 计算时间 ≥ 通信时间，整体 wallclock ≈ N × attention 时间，**通信被完全隐藏**。Ulysses 是"先 a2a 再算"，无法重叠（attention 必须等所有 head 数据到齐）。

#### G. 通信量对比

设序列总长 S、heads H、hidden D、N 卡：

| 算法 | 单卡发送量 | 总通信量 | 是否能重叠 |
|------|----------|---------|-----------|
| Ulysses（QKV 各 1 次 a2a） | 3 × S × H/N × D | 3 × S × H × D | 否 |
| Ring（N−1 步 KV 传） | (N−1) × 2 × S/N × H × D | 2(N−1) × S × H × D | 是 |

数字上 Ring 的总通信量约是 Ulysses 的 `2(N−1)/3` 倍。N=4 时是 2×，N=8 时是 4.67×——但因为可以**和计算重叠**，实际 wallclock 经常比 Ulysses 还快，尤其在序列长、attention 计算重的场景。

#### H. FP8 / FP4 通信压缩

Ring 也支持 `use_fp8_comm` / `use_fp4_comm` / `use_tensor_fusion`（`ring_attn.py:54-67`）：

- `_send_recv_tensor` 内部先量化 → 传量化值 + scale → 接收方反量化。
- `use_tensor_fusion=True` 时把 K、V 在 dim=0 stack 成 `kv` 一起传，减少一次 P2P 启动开销（n=2 → 1）。

注意 Ring **不支持 `enable_head_parallel`**（`ring_attn.py:84` 有 assert）——因为 Ring 的并行维度本来就是 seq，head 维度上每张卡都已经是完整的，再切 head 没有意义。

#### I. 何时选 Ring 而非 Ulysses

| 场景 | 选择 |
|------|------|
| `heads % world_size != 0`（GQA 小、Mistral 类模型） | **Ring**（Ulysses 直接挂） |
| 跨节点 IB 带宽受限 | **Ring**（计算可隐藏通信） |
| 头数大、单步 attention 短（图像模型） | **Ulysses**（通信总量更小、重叠收益小） |
| 长视频 DiT、attention 占主导 | **Ring**（重叠收益最大） |

LightX2V 把两个算子都注册到 `ATTN_WEIGHT_REGISTER`，配置项 `seq_p_attn_type` 一行切换，方便针对不同模型调优。

#### J. 一句话总结

> **Ulysses = 一次重排，等价单卡**；**Ring = N 步流水线，靠 LSE 合 softmax，通信和计算重叠**。前者通信省、后者通用性好且能隐藏通信。

## 第四部分：Tensor 并行

### 12. 现状：仅在部分模型路径打开

**核心文件**：`lightx2v/models/networks/ltx2/weights/transformer_weights.py:163`

LTX2 等模型在权重加载时按 `tp_rank` 切分线性层（列切 / 行切），`norm` 层使用 `RMS_WEIGHT_REGISTER["TensorParallel"]` 做 TP 友好的归一化。

**TP 与 CFG/SP 互斥**的原因（回顾 §1）：TP 需要每层 forward 后做 `all_reduce`，与 SP 的 `all_to_all` 通信图、CFG 的"两条独立路径"不容易同时维护。当前框架选择"模型设计期决定走哪条路"，不做混合。

### 13. TP vs SP 的取舍

| 维度 | Tensor 并行 | 序列并行（Ulysses） |
|------|-------------|---------------------|
| 切什么 | hidden / heads | seq |
| 显存收益 | 权重切分，显存几乎线性下降 | 权重不切，仅激活切分 |
| 通信 | 每层 all_reduce（同步多） | 每个 attention 2× all_to_all |
| 适合场景 | 权重装不下（大 LLM） | 序列特别长（长视频 DiT） |
| 代码改动 | 权重加载 + matmul 切法都要改 | 只需在 attention 算子做 all_to_all |

LightX2V 的核心场景是"权重能装下、序列特别长"的视频 DiT，所以 SP 是主线，TP 仅作为兼容路径存在。

## 第五部分：二维并行组合

### 14. CFG × Seq 的二维 mesh

```
# 假设 8 卡：cfg_p_size=2, seq_p_size=4
# device_mesh shape = (2, 4)
#                       cfg_p   seq_p
#   rank 0  →  cfg_p=0, seq_p=0     ┐
#   rank 1  →  cfg_p=0, seq_p=1     │  cond 半组（4 卡 SP）
#   rank 2  →  cfg_p=0, seq_p=2     │
#   rank 3  →  cfg_p=0, seq_p=3     ┘
#   rank 4  →  cfg_p=1, seq_p=0     ┐
#   rank 5  →  cfg_p=1, seq_p=1     │  uncond 半组（4 卡 SP）
#   rank 6  →  cfg_p=1, seq_p=2     │
#   rank 7  →  cfg_p=1, seq_p=3     ┘
```

**通信结构**：

- `cfg_p_group`：每行一组（rank 0&4、1&5、2&6、3&7），仅在最后 all_gather 一次 noise_pred。
- `seq_p_group`：每列一组（rank 0~3、4~7），attention 内部多次 all_to_all。

每个 rank 的负载 = cond 或 uncond 中的一份 × seq 总长度的 1/4，**理论加速 8×**（实际打折取决于 seq_p 通信占比）。

## 第六部分：开销与选型

### 16. 显存 / 通信 / 计算开销对比

| 配置 | 权重显存 | 激活显存 | 通信开销 | 适用 |
|------|---------|---------|---------|------|
| 单卡 | 100% | 100% | 0 | 小尺寸快验证 |
| CFG 2卡 | 100%（每卡都装） | 100% | 1× all_gather/step | 单卡能装下、要 2× 加速 |
| Ulysses 4 卡 | 100% | 25% | 每层 2× all_to_all | 长视频、高分辨率 |
| CFG×Ulysses 8 卡 | 100% | 25% | a2a + 1× all_gather | 720p+ 长视频生产 |
| TP 8 卡（LTX2） | 12.5% | 12.5% | 每层 all_reduce | 巨型权重模型 |

### 17. 选型建议

1. **优先看显存**：权重装得下 → CFG/SP 优先；装不下 → 上 TP。
2. **CFG 几乎免费**：只要 `enable_cfg=True` 就值得开 `cfg_p_size=2`。
3. **超过 2 卡时叠 SP**：4/8/16 卡都用 `cfg_p_size=2 × seq_p_size=N/2`。
4. **head 数少（GQA 小）**：换 `seq_p_attn_type=ring`。
5. **跨节点带宽差**：开 `seq_p_fp8_comm`（甚至 fp4）压通信量。
6. **极致优化**：`seq_p_tensor_fusion=true` 把 q/k/v 三次 a2a 合一次。
