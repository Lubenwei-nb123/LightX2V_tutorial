## 第一部分：为什么需要分离部署

## 1. 单体推理的资源瓶颈

第10课的 Server 架构中，一个进程加载全部组件（T5 + CLIP + VAE + DiT），在一张 GPU 上串行执行。以 Wan 2.1 I2V 14B 为例：

```
单体推理的 GPU 时间线
  ┌─────┬──────┬──────────────────────────────────┬────────┐
  │ T5  │ CLIP │         DiT 去噪（40步）          │  VAE   │
  │ 编码│ 编码 │                                    │  解码  │
  │ 5s  │ 0.1s │          120s                      │  8s    │
  └─────┴──────┴──────────────────────────────────┴────────┘
  ↑                                                        ↑
  请求到达                                              视频输出
  
  总耗时 ≈ 133s，GPU 利用率分析：
  - DiT 占 90% 时间，是 GPU 算力密集型
  - T5/CLIP/VAE 占 10% 时间，但各自需要独立的模型权重
```

**问题**：

| 阶段 | GPU 特性 | 显存占用 | 算力需求 |
|------|---------|---------|---------|
| Encoder（T5+CLIP+VAE） | 计算稀疏，显存大 | ~7 GB | 低 |
| Transformer（DiT） | 计算密集 | ~15-35 GB | 极高 |
| Decoder（VAE 解码） | 计算中等 | ~0.5 GB | 中 |

单体模式下，DiT 推理占 90% 时间，但 T5/CLIP/VAE 的 7+ GB 权重始终占据 GPU 显存。如果把 Encoder 和 Decoder 放到其他 GPU（或与 Encoder 共享 GPU），DiT 就能独占一张完整的 GPU。

**分离部署的收益**：
1. **Transformer GPU 独占**：DiT 权重 + 双缓冲 Offload 可以充分利用显存
2. **Encoder/Decoder 共享 GPU**：T5+CLIP+VAE 编码只占几秒，编码完成后显存可给 VAE 解码复用
3. **流水线并行**：请求 A 的 Transformer 推理与请求 B 的 Encoder 编码可以重叠

### 2.1 两层通信机制

分离部署使用**两层通信**：

| 层次 | 用途 | 载体 | 数据量 |
|------|------|------|--------|
| 控制面 | 请求配置分发、元数据传递 | RDMA Ring Buffer（JSON 序列化） | 几 KB |
| 数据面 | 张量传输（编码结果、latents） | Mooncake Transfer Engine | 几百 MB |

**为什么分两层？** 控制面的数据小但频繁（每个请求一次），适合固定大小的 Ring Buffer。数据面的数据大但不频繁（每个 Phase 一次），适合 Mooncake 的大块零拷贝传输。

### 2.2 两个 Phase 的数据内容

**Phase1：Encoder → Transformer**

```python
# encoder.py 发送的 buffer 列表：
buffer[0] = context          # T5 文本编码 [1, 512, 4096]     ~4 MB
buffer[1] = context_null     # CFG 负面文本编码（可选）         ~4 MB
buffer[2] = clip_encoder_out # CLIP 图像编码（I2V 专用）       ~0.5 MB
buffer[3] = vae_encoder_out  # VAE 编码结果 [5, 81, H, W]    ~200 MB
buffer[4] = latent_shape     # [4] int64                      32 bytes
buffer[5] = meta_json        # SHA256 校验 + shape/dtype 信息  ~1 KB
```

**Phase2：Transformer → Decoder**

```python
# transformer.py 发送的 buffer 列表：
buffer[0] = latents          # 去噪后 latent [16, 21, H, W]  ~200 MB
buffer[1] = meta_json        # SHA256 校验 + shape/dtype 信息  ~1 KB
```

## 3. 什么是 RDMA

### 3.1 传统网络 vs RDMA

**传统 TCP/IP 收发数据的路径**：

```
应用程序 A (用户态)                              应用程序 B (用户态)
    │ write(socket, buf)                             ▲ read(socket, buf)
    ▼                                                │
  内核态                                           内核态
    │ 1. 从用户空间拷贝到内核缓冲区                     │ 5. 从内核缓冲区拷贝到用户空间
    ▼                                                │
  TCP/IP协议栈                                    TCP/IP协议栈
    │ 2. 封装 TCP/IP 头                              │ 4. 解析 TCP/IP 头
    ▼                                                │
  网卡驱动                                         网卡驱动
    │ 3. DMA 到网卡 → 线缆 → 网卡 → 中断 → 驱动 ──→│
    ▼                                                │
  ─────────────── 物理网络 ────────────────────────────
```

这个路径有三个性能杀手：
1. **多次内存拷贝**：用户态 → 内核态 → 网卡（发送）；网卡 → 内核态 → 用户态（接收）
2. **内核介入**：每次收发都需要系统调用（上下文切换），协议栈处理占用 CPU
3. **中断开销**：网卡收到数据后产生硬件中断，CPU 处理中断上下文

**RDMA（Remote Direct Memory Access）直接消除了以上全部问题**：

```
应用程序 A (用户态)                              应用程序 B (用户态)
    │ post_send(WR)                                  （什么都不用做）
    ▼                                                     ▲
  RDMA 网卡(RNIC)                                   RDMA 网卡(RNIC)
    │ 1. 直接 DMA 读取用户态内存                        │ 2. 直接 DMA 写入用户态内存
    └─────────── RDMA 网络 ───────────────────────────┘
                 （硬件完成全部工作）
```

关键特性：
- **零拷贝（Zero-Copy）**：RNIC 直接 DMA 读写应用程序的用户态内存，不经过内核缓冲区
- **内核旁路（Kernel Bypass）**：应用程序直接向 RNIC 提交请求，不需要系统调用
- **CPU 零参与**：单边操作（RDMA Read/Write）中，远端 CPU 完全不知道数据在被读写
- **硬件协议卸载**：可靠传输（重传、确认、排序）全部由 RNIC 硬件完成

### 3.2 RDMA 的硬件生态

RDMA 不是一个协议，而是一种能力，有三种主流实现：

| 实现 | 全称 | 网络 | 典型延迟 | 典型带宽 | 说明 |
|------|------|------|---------|---------|------|
| **InfiniBand** | — | 专用 IB 交换机 | ~1 μs | 200-400 Gbps (HDR/NDR) | GPU 集群标配，NVIDIA 主导 |
| **RoCE v2** | RDMA over Converged Ethernet | 普通以太网交换机 | ~2-5 μs | 100-400 Gbps | 无需专用交换机，但需要无损网络（PFC/ECN） |
| **iWARP** | Internet Wide Area RDMA Protocol | 普通以太网 | ~5-10 μs | 25-100 Gbps | 支持有损网络，但性能最差，已边缘化 |

AI 训练/推理集群中最常见的是 **InfiniBand**（如 A100/H100 集群标配 ConnectX-7 网卡 + QM9790 交换机），以及 **RoCE v2**（成本更低的替代方案）。

LightX2V 的 `rdma_client.py` 使用 `pyverbs` 库（libibverbs 的 Python 绑定），兼容 InfiniBand 和 RoCE：

```python
# rdma_client.py:8-9
from pyverbs.device import Context, get_device_list   # 枚举 RDMA 设备
from pyverbs.mr import MR                             # Memory Region 注册
```

### 3.3 RDMA Verbs 编程模型

RDMA 编程的核心 API 叫做 **Verbs**（动词），因为每个操作都是一个动作：create、register、post、poll。下面用 LightX2V 代码中的实际对象来解释每个概念：

```
┌───────────────────────────────────────────────────────────────┐
│                         应用程序                               │
│                                                               │
│   ① Context ──→ 打开 RDMA 设备                                │
│       │                                                       │
│   ② PD (Protection Domain) ──→ 隔离命名空间                    │
│       │                                                       │
│   ③ MR (Memory Region) ──→ 注册内存，获取 lkey/rkey            │
│       │                   （rkey 发给对端，用于远程访问）        │
│       │                                                       │
│   ④ CQ (Completion Queue) ──→ 完成通知队列                     │
│       │                                                       │
│   ⑤ QP (Queue Pair) = SQ + RQ ──→ 通信端点                    │
│       │   SQ: Send Queue 发送队列                              │
│       │   RQ: Receive Queue 接收队列                           │
│       │                                                       │
│   ⑥ WR (Work Request) ──→ 描述一次操作（写/读/原子）           │
│       │                                                       │
│   ⑦ SGE (Scatter-Gather Entry) ──→ 内存段描述                  │
│                                                               │
│   工作流：构造 WR → post_send(WR) → RNIC 执行 → poll CQ 确认  │
└───────────────────────────────────────────────────────────────┘
```

对应到代码中的创建顺序（`rdma_client.py:43-62`）：

```python
# ① 打开 RDMA 设备
self.ctx = IBDevice(iface_name).open()       # Context

# ② 创建保护域
self.pd = PD(self.ctx)                        # Protection Domain

# ③ 创建完成队列
self.cq = CQ(self.ctx, 10)                   # Completion Queue，容量 10

# ④ 创建 Queue Pair (RC 类型 = 可靠连接)
qp_init_attr = QPCap(max_send_wr=10, max_recv_wr=10,
                     max_send_sge=1, max_recv_sge=1)
qia = QPInitAttr(qp_type=QPType.RC,          # Reliable Connected
                 scq=self.cq, rcq=self.cq,   # 收发共用一个 CQ
                 cap=qp_init_attr)
self.qp = QP(self.pd, qia, qa)

# ⑤ 注册本地内存（客户端用于暂存发送/接收的数据）
self.local_mr = MR(self.pd, self.buffer_size, AccessFlag.LOCAL_WRITE)
```

**各概念详解**：

| 概念 | 类比 | 说明 |
|------|------|------|
| **Context** | 文件句柄 | 打开一个 RDMA 设备，后续所有操作都基于此 |
| **PD** | 进程地址空间 | 同一 PD 内的 QP 和 MR 可以互相访问，不同 PD 隔离 |
| **MR** | mmap + 注册 | 告诉 RNIC "这块内存你可以直接 DMA"。注册后返回 lkey（本地访问凭证）和 rkey（远程访问凭证）。rkey 需要告诉对端，否则对端无法访问 |
| **CQ** | epoll | 操作完成后 RNIC 往 CQ 里放一个 WC（Work Completion），应用 poll 取结果 |
| **QP** | TCP socket | 一对一的通信端点。RC 类型 = TCP（可靠有序），UD 类型 = UDP（不可靠无连接） |
| **WR** | sendmsg 的参数 | 描述一次操作：类型（Write/Read/FAA/CAS）+ 本地内存(SGE) + 远端地址 |
| **SGE** | iovec | 描述一段本地内存：(地址, 长度, lkey) |

### 3.4 QP 状态机

QP 创建后不能直接使用，必须经过状态转换（类似 TCP 的三次握手）：

```
  RESET ──→ INIT ──→ RTR ──→ RTS
                     (Ready    (Ready
                      To        To
                      Receive)  Send)
```

每个状态转换需要设置不同参数：

| 转换 | 设置内容 | 对应代码 |
|------|---------|---------|
| → INIT | port_num, access_flags（允许远程读/写/原子） | `qp.to_init(init_attr)` |
| → RTR | 对端 QPN, PSN, GID, MTU（这些信息通过 TCP 带外交换） | `qp.to_rtr(rtr_attr)` |
| → RTS | 本地 PSN, timeout, retry_cnt | `qp.to_rts(rts_attr)` |

LightX2V 的连接建立流程（`rdma_server.py:168` + `rdma_client.py:78`）：

```
Server                                          Client
  │                                                │
  │  ①  TCP listen(port=5566)                      │
  │  ◀──────── TCP connect ────────────────────────│
  │                                                │
  │  ②  发送 {addr, rkey, qpn, psn, gid}           │
  │  ──────────────────────────────────────────────▶│
  │                                                │
  │  ③  接收 {qpn, psn, gid}                       │
  │  ◀──────────────────────────────────────────────│
  │                                                │
  │  ④  双方各自执行 INIT → RTR → RTS               │
  │                                                │
  │  ⑤  QP 就绪，可以进行 RDMA 操作                  │
  │     Server 的 MR 对 Client 可见                  │
```

**关键洞察**：TCP 只用于初始的信息交换（带外通道），一旦 QP 建立连接，后续所有数据传输都走 RDMA 通道，不再经过 TCP。这个设计在代码中也能看到——`rdma_client.py:104` 保存了 `self.sock`，但后续的 `rdma_write`/`rdma_read` 操作完全不使用它。

### 3.5 RDMA 的三类操作

#### 双边操作（Two-Sided）：Send / Receive

最传统的方式，类似 TCP 的 send/recv：
- 发送方 post_send(SEND WR)
- 接收方**必须预先** post_recv(RECV WR) 准备好接收缓冲区
- 两边 CPU 都参与

LightX2V **没有使用双边操作**，因为它需要接收方预先准备，增加了协调复杂度。

#### 单边操作（One-Sided）：RDMA Write / RDMA Read

这是 RDMA 的精华——远端 CPU 完全不知道数据在被读写：

**RDMA Write**（`rdma_client.py:134`）：
```python
def rdma_write(self, data_bytes):
    # 1. 数据写入本地 MR
    self.local_mr.write(padded, len(padded), 0)

    # 2. 构造 WR：指定操作类型 + 本地内存 + 远端地址
    sge = SGE(self.local_mr.buf, len(data_bytes), self.local_mr.lkey)
    wr = WR(opcode=WROpcode.RDMA_WRITE, sg=[sge],
            send_flags=e.IBV_SEND_SIGNALED)
    wr.set_wr_rdma(remote_rkey, remote_addr)   # 指向 Server 的 MR

    # 3. 提交给 RNIC
    self.qp.post_send(wr)

    # 4. 等待完成
    self._poll_cq()
```

执行过程（硬件层面）：
```
Client RNIC                              Server RNIC
    │ DMA 读取 Client MR                      │
    │ (client 用户态内存)                      │
    ├──── RDMA Write packet ────────────────→│
    │                                         │ DMA 写入 Server MR
    │                                         │ (server 用户态内存)
    │                                         │
    │ ← ACK ──────────────────────────────────│
    │                                         │
  CQ 中出现 WC                            Server CPU 无感知！
```

**RDMA Read**（`rdma_client.py:167`）：
```
Client RNIC                              Server RNIC
    │                                         │
    ├──── RDMA Read Request ─────────────────→│
    │                                         │ DMA 读取 Server MR
    │ ← RDMA Read Response (带数据) ──────────│
    │ DMA 写入 Client MR                      │
    │                                         │
  CQ 中出现 WC                            Server CPU 无感知！
```

#### 原子操作（Atomic）：Fetch-And-Add / Compare-And-Swap

远端原子读-修改-写，**在 RNIC 硬件中原子完成**，适合实现分布式锁和计数器。

**Fetch-And-Add（FAA）**（`rdma_client.py:217`）：
```python
def rdma_faa(self, remote_addr, add_value):
    sge = SGE(self.local_mr.buf, 8, self.local_mr.lkey)   # FAA 操作固定 8 字节
    wr = WR(opcode=WROpcode.ATOMIC_FETCH_AND_ADD, sg=[sge],
            send_flags=e.IBV_SEND_SIGNALED)
    wr.set_wr_atomic(target_rkey, remote_addr, add_u64, 0)

    self.qp.post_send(wr)
    self._poll_cq()

    # 返回值是修改前的旧值（原子地返回旧值 + 加上新值）
    old = self.local_mr.read(8, 0)
    return int.from_bytes(old, byteorder="big", signed=False)
```

```
Client RNIC                              Server RNIC
    │                                         │
    ├──── FAA Request(addr, +1) ─────────────→│
    │                                         │ 原子操作：
    │                                         │   old = *addr
    │                                         │   *addr = old + 1
    │ ← FAA Response(old_value) ──────────────│
    │                                         │
  本地 MR 中得到 old_value                  Server CPU 无感知！
```

**FAA 在 LightX2V 中的关键作用**：Ring Buffer 的 head/tail 指针就是通过 FAA 实现无锁递增的（`rdma_buffer.py:236, 276`），它的核心价值是让 slot 预留不必依赖全局锁。至于“多个消费者是否能安全共享同一个 ring”，还要看远端原子实现和上层分发设计，当前仓库并没有把这件事当成默认成立的前提。

### 3.6 Memory Registration 深入理解

RDMA 要求参与传输的内存必须**预先注册**。注册做了两件事：

1. **页锁定（Pin）**：调用 `mlock()` 将虚拟页固定到物理页，防止被 OS swap out。如果 RNIC 正在 DMA 读写一个被 swap 的页面，数据就损坏了。

2. **地址翻译表**：RNIC 需要知道虚拟地址到物理地址的映射，注册时 OS 会将页表信息写入 RNIC 的内部 TLB。

```python
# rdma_server.py:78-82
self.mr = MR(
    self.pd, self.buffer_size,
    AccessFlag.LOCAL_WRITE |       # 本地可写
    AccessFlag.REMOTE_WRITE |      # 远端可写（RDMA Write 目标）
    AccessFlag.REMOTE_READ |       # 远端可读（RDMA Read 源）
    AccessFlag.REMOTE_ATOMIC       # 远端可原子操作（FAA/CAS 目标）
)
```

**与仓库中另一份 SharedMemory 权重共享设计文档的联系**：`cudaHostRegister` 和 RDMA 的 `MR` 注册本质相同——都是将一段用户态内存注册到 DMA 引擎（GPU 或 RNIC），使硬件可以直接访问。区别是 `cudaHostAlloc`/`cudaHostRegister` 注册到 GPU DMA 控制器，`MR` 注册到 RNIC DMA 控制器。

### 3.7 Mooncake Transfer Engine

LightX2V 的大张量传输使用 [Mooncake](https://github.com/kvcache-ai/Mooncake) Transfer Engine，而不是直接用 RDMA Verbs。原因是 Verbs API 太底层了——需要手动管理 QP 连接、MR 注册、分片传输。Mooncake 封装了这些细节：

```python
# mooncake.py 核心接口
class MooncakeTransferEngine:
    def __init__(self):
        from mooncake.engine import TransferEngine
        self.engine = TransferEngine()

    def register(self, ptr, length):
        """注册内存（内部调用 ibv_reg_mr）"""
        self.engine.register_memory(ptr, length)

    def transfer_sync(self, session_id, buffer, peer_buffer_address, length):
        """同步传输（内部使用 RDMA Write）"""
        self.engine.transfer_sync_write(session_id, buffer, peer_buffer_address, length)
```

**Mooncake 做了什么 Verbs 不做的事**：

| 能力 | Verbs 手动管理 | Mooncake |
|------|--------------|----------|
| 连接管理 | 手动 TCP 交换 QP 信息 + 状态转换 | 自动发现（通过 metadata server） |
| 内存注册 | 手动 `MR()` 创建 | `register_memory(ptr, len)` |
| 大数据传输 | 需要自己分片（单个 WR 有大小限制） | 自动分片 + 流控 |
| 多设备 | 手动选择网卡 | 自动选择最优路径 |
| 传输协议 | 纯 RDMA | 支持 RDMA / TCP fallback |

**LightX2V 中两层传输的分工**：

```
               小数据 (请求配置 JSON, ~KB)          大数据 (编码结果/latents, ~MB)
                        │                                    │
                        ▼                                    ▼
              RDMA Ring Buffer                      Mooncake Transfer Engine
            (直接用 Verbs API)                    (封装了 RDMA Verbs)
                        │                                    │
               rdma_client.py                          mooncake.py
               rdma_server.py                              │
               rdma_buffer.py                     mooncake.engine.TransferEngine
                        │                                    │
                        └───────── 底层都是 ──────────────────┘
                                  libibverbs
                                     │
                                 RDMA 网卡 (RNIC)
```

Ring Buffer 直接使用 Verbs 是因为它的操作很简单（8 字节 FAA + 4KB slot Read/Write），不需要 Mooncake 的高层封装。而编码结果和 latents 动辄几百 MB，需要 Mooncake 的自动分片和流控。

### 3.8 RDMA 性能数字感知

帮助建立直觉，以下是典型数据中心的 RDMA 性能数据：

| 指标 | InfiniBand HDR (200Gbps) | RoCE v2 (100Gbps) | PCIe 4.0 x16 |
|------|-------------------------|-------------------|--------------|
| 单向带宽 | ~24 GB/s | ~12 GB/s | ~32 GB/s |
| 延迟（小消息） | ~1 μs | ~2-3 μs | ~2-5 μs (DMA) |
| IOPS (4KB) | ~30M | ~15M | — |

对比分离部署中的数据量：

| 数据 | 大小 | InfiniBand HDR 传输时间 | RoCE 100G 传输时间 |
|------|------|----------------------|------------------|
| Ring Buffer slot (JSON 配置) | ~4 KB | ~0.2 μs | ~0.3 μs |
| T5 context 编码 | ~4 MB | ~0.17 ms | ~0.33 ms |
| VAE 编码结果 | ~200 MB | ~8.3 ms | ~16.7 ms |
| DiT latents | ~200 MB | ~8.3 ms | ~16.7 ms |

相比 DiT 去噪的 120 秒，数据传输时间（毫秒级）完全可以忽略。这正是分离部署可行的基础。

## 第四部分：RDMA Ring Buffer

## 4. Ring Buffer 的设计

**核心文件**：`lightx2v/disagg/rdma_buffer.py`

RDMA Ring Buffer 可以理解成一个固定 slot 的轻量元数据队列。**在当前仓库的主路径里，最好把它按“单生产者 + 单消费者”来理解**：一个 ring 对应一条阶段边（Controller→Encoder、Encoder→Transformer、Transformer→Decoder）。

`rdma_buffer.py` 的类注释还明确提醒了一点：如果多个客户端同时对同一个 ring 调 `consume()`，正确性会依赖远端原子 FAA 的实现质量，代码当前并不把“同一个 ring 的高并发多消费者”当成默认安全用法。所以后面讲多实例调度时，要把它理解成“策略层已经有了，但真正的多消费者安全分发还需要额外接线”。

### 4.1 内存布局

```
RDMA 注册内存（连续）：
┌──────────┬──────────┬──────────┬──────────┬───┬──────────┐
│  head(8B)│  tail(8B)│  slot[0] │  slot[1] │...│slot[N-1] │
└──────────┴──────────┴──────────┴──────────┴───┴──────────┘
│← 16 B →│           │←── N × slot_size ──────────────────→│

head: 消费者的读取位置（消费后 +1）
tail: 生产者的写入位置（写入后 +1）
slot: 固定大小（默认 4096B），存放 JSON 序列化的配置

可用数据量 = tail - head
空闲空间   = buffer_size - (tail - head)
```

### 4.2 生产者（produce）

```python
# rdma_buffer.py:230-259
def produce(self, config: dict) -> int:
    # 1. 原子递增 tail（RDMA FAA 操作）
    old_tail = self._rdma_faa(self.descriptor.tail_addr, 1)

    # 2. 检查是否满（对比 head）
    cur_head = self._read_remote_u64(self.descriptor.head_addr)
    used = (old_tail + 1) - cur_head
    if used > self.buffer_size:
        self._rdma_faa(self.descriptor.tail_addr, -1)  # 回滚
        raise BufferError("ring buffer is full")

    # 3. 序列化 config 为 JSON bytes
    payload = self._serialize_config(config)
    # 格式: [4B payload_length][JSON bytes][padding]

    # 4. 写入 slot
    slot_idx = old_tail % self.buffer_size
    slot_addr = self.descriptor.slot_addr + slot_idx * self.slot_size
    self._rdma_write_bytes(slot_addr, payload)
    return slot_idx
```

### 4.3 消费者（consume）

```python
# rdma_buffer.py:261-300
def consume(self) -> Optional[dict]:
    # 1. 检查是否有数据
    cur_head = self._read_remote_u64(self.descriptor.head_addr)
    cur_tail = self._read_remote_u64(self.descriptor.tail_addr)
    if cur_head >= cur_tail:
        return None  # 空

    # 2. 原子递增 head（RDMA FAA 操作）
    old_head = self._rdma_faa(self.descriptor.head_addr, 1)
    if old_head >= cur_tail:
        self._rdma_faa(self.descriptor.head_addr, -1)  # 竞争失败，回滚
        return None

    # 3. 读取 slot 数据
    slot_idx = old_head % self.buffer_size
    slot_addr = self.descriptor.slot_addr + slot_idx * self.slot_size
    raw = self._rdma_read_bytes(slot_addr, self.slot_size)

    # 4. 反序列化
    return self._deserialize_config(raw)
```

### 4.4 三个 Ring Buffer 的用途

Controller 创建了**三个独立的 Ring Buffer**：

| Ring Buffer | 生产者 | 消费者 | 用途 |
|------------|--------|--------|------|
| `request` | Controller | Encoder | 分发推理请求配置 |
| `phase1` | Encoder | Transformer | 传递编码元数据 + Mooncake 会话信息 |
| `phase2` | Transformer | Decoder | 传递 latent 元数据 + Mooncake 会话信息 |

**注意**：Ring Buffer 只传递**小数据**（JSON 配置、Mooncake 会话 ID）。实际的大张量传输通过 Mooncake Transfer Engine 完成，Ring Buffer 中传递的是 Mooncake 需要的连接参数。

```python
def run(self, stop_event=None):

    exec_queue = deque()         # 待执行的请求
    complete_queue = {}          # 等待传输完成的请求

    while True:
        # 1. 从 request Ring Buffer 消费新请求
        if self._request_rdma_buffer is not None:
            config = self._request_rdma_buffer.consume()
            if config is not None:
                req_queue.append(config)

        # 2. 初始化请求（分配 RDMA buffer、建立 Mooncake 连接）
        if req_queue:
            config = req_queue.popleft()
            self.init(config)          # 分配 buffer + 连接 Mooncake

        # 3. 执行编码
        if exec_queue:
            room, config = exec_queue.popleft()

            complete_queue[room] = config

            if status == DataPoll.Success:
                self.remove(room)      # 释放 buffer
```

## 7. TransformerService：去噪阶段

**核心文件**：`lightx2v/disagg/services/transformer.py`

Transformer 是最核心的服务——它**接收** Encoder 的编码结果，执行去噪循环，再**发送** latents 给 Decoder。

### 7.1 双向数据流

```
          Phase1（接收）                    Phase2（发送）
    Encoder ──────→ Transformer ──────→ Decoder
    
    data_mgr1 + data_receiver          data_mgr2 + data_sender
    rdma_buffer1[]                     rdma_buffer2[]
```

### 7.2 事件循环（比 Encoder 多一个 `waiting_queue`）

```python
def run(self, stop_event=None):
    req_queue = deque()          # 从 phase1 Ring 收到的请求
    waiting_queue = {}           # 等待 Mooncake 接收完成
    exec_queue = deque()         # 接收完成，待执行去噪
    complete_queue = {}          # 去噪完成，等待 Phase2 发送完成

    while True:
        # 1. 从 phase1 Ring Buffer 消费元数据
        packet = self._phase1_rdma_buffer.consume()
        if packet:
            config = packet["request_config"]
            config["encoder_node_address"] = packet["encoder_node_address"]
            req_queue.append(config)

        # 2. 初始化（分配 Phase1 接收 buffer + Phase2 发送 buffer）
        if req_queue:
            config = req_queue.popleft()
            self.init(config)
            waiting_queue[room] = config

        # 3. 轮询 Phase1 接收状态
        for room in list(waiting_queue):
            status = self.data_receiver[room].poll()
            if status == DataPoll.Success:    # 编码数据接收完成
                exec_queue.append(waiting_queue.pop(room))

        # 4. 执行去噪
        if exec_queue:
            room, config = exec_queue.popleft()
            self.process(config)              # 去噪 + 发送 latents
            complete_queue[room] = config

        # 5. 轮询 Phase2 发送状态
        for room in list(complete_queue):
            status = self.data_sender[room].poll()
            if status == DataPoll.Success:
                self.remove(room)
```

## 9. 传输协议设计

**核心文件**：`lightx2v/disagg/protocol.py`

```python
@dataclass
class AllocationRequest:
    bootstrap_room: int          # 请求 ID（传输 slot/session 的唯一标识）
    buffer_sizes: List[int]      # 预计算的 buffer 大小列表

@dataclass
class RemoteBuffer:
    addr: int                    # RDMA 注册内存地址

@dataclass
class MemoryHandle:
    buffers: List[RemoteBuffer]  # 分配的 buffer 列表
```

### 9.1 `bootstrap_room` 的作用

每个请求分配一个唯一的 `bootstrap_room`（整数 ID），用于：
1. **Mooncake 连接标识**：建立 Encoder ↔ Transformer ↔ Decoder 的点对点传输通道
2. **Buffer 隔离**：不同请求的 buffer 通过 `room` 索引互不干扰
3. **生命周期管理**：请求完成后 `remove(room)` 释放该 room 的所有资源

### 9.2 SHA256 校验

每次传输都附带 SHA256 校验，确保跨节点传输的数据完整性：

```python
def _sha256_tensor(tensor):
    data = tensor.detach().to(torch.float32).contiguous().cpu().numpy().tobytes()
    return hashlib.sha256(data).hexdigest()
```

接收端在 `process()` 中逐一校验：
- `context_hash`：文本编码
- `clip_hash`：CLIP 编码
- `vae_hash`：VAE 编码
- `latents_hash`：去噪 latents

**注意**：SHA256 校验有性能开销（需要 GPU→CPU 拷贝 + 计算哈希），生产环境可以关闭。当前实现中，所有校验都是强制的。

## 第七部分：调度与监控

## 10. Round-Robin 调度（当前更像预留扩展点）

**核心文件**：`lightx2v/disagg/scheduler/round_robin.py`

```python
class RoundRobinPolicy(SchedulingPolicy):
    def __init__(self):
        self._instances: list[str] = []  # 实例地址列表
        self._next_index = 0
        self._lock = Lock()

    def schedule(self) -> str:
        with self._lock:
            selected = self._instances[self._next_index]
            self._next_index = (self._next_index + 1) % len(self._instances)
            return selected
```

Controller 确实为 Encoder、Transformer、Decoder 各维护了一个 `RoundRobinPolicy`，也提供了 `add_instance()` / `remove_instance()` 来注册实例地址。

**但要注意当前代码状态**：默认 `ControllerService.run()` / `send_request()` 的主链路里，Controller 只是把请求写进统一的 `request` RDMA ring，并**没有真正调用** `encoder_policy.schedule()`、`transformer_policy.schedule()` 或 `decoder_policy.schedule()`。

所以把当前仓库里的 Round-Robin 理解成下面这个状态更准确：

1. **调度策略类已经写好**：`scheduler/round_robin.py` 提供了轮询选址能力。
2. **Controller 也已经有实例注册表**：可以记录多个 Encoder / Transformer / Decoder 地址。
3. **但默认分发路径还没完全接上**：请求仍然是写入共享 ring，而不是先 `schedule()` 再发送到某个实例专属入口。

这也和上一节 Ring Buffer 的限制一致：如果要真正支持多个同类实例并行消费，除了策略本身，还要补上“每个实例怎么被安全地选中并消费”的链路设计。

## 11. Monitor / Reporter 健康检查

**核心文件**：`lightx2v/disagg/monitor.py`

每个服务（Encoder/Transformer/Decoder）启动一个 `Reporter` 守护线程，通过 ZMQ REP 端口暴露指标：

```python
class Reporter:

        }
        # GPU 指标（通过 nvidia-smi）
        metrics.update(self._query_gpu_metrics())
        # → gpu_utilization, gpu_memory_used_mb, gpu_memory_total_mb

        # 队列指标（由服务注入）
        extra = self._extra_metrics_provider()
        # → queue_sizes, queue_total_pending, all_queues_empty
        metrics.update(extra)
        return metrics
```

`Monitor` 类本身已经实现了“Controller 主动轮询各服务”的逻辑：

```python
class Monitor:
    def poll_once(self) -> List[dict]:
        return [self._poll_one(addr) for addr in self.nodes]
        # 通过 ZMQ REQ/REP 逐个查询
```

**但当前默认代码路径里，这套监控没有自动常驻跑起来**：`ControllerService.run()` 确实创建了 `monitor_thread`，但 `monitor_thread.start()` 目前是注释掉的。所以更准确的表述应该是：

- `Reporter` 已经在 Encoder / Transformer / Decoder 构造阶段真实启动。
- `Monitor` 基础设施已经具备。
- 默认示例并不会持续打印健康检查结果，除非你手动开启 Controller 侧的轮询线程。

## 12. 配置文件结构

先区分“逻辑角色”和“当前仓库里的常用运行形态”：

- **逻辑角色**仍然是 4 个：Controller / Encoder / Transformer / Decoder。
- **当前 Wan HTTP 脚本的常用部署形态**是 3 个常驻服务：Encoder、Transformer、Decoder。
- 请求入口通常不是一个长期常驻的 Controller 进程，而是 `scripts/server/disagg/wan/post_wan_t2v.py` 这类脚本按顺序把请求打到三个服务上。
- 如果你想看“4 个角色在一个 Python 进程里怎么串起来”的最小闭环，参考 `lightx2v/disagg/examples/wan_t2v_service.py`。

当前仓库里与 Wan T2V 相关的配置路径是：

- `configs/disagg/wan/wan_t2v_disagg_encoder.json`
- `configs/disagg/wan/wan_t2v_disagg_transformer.json`
- `configs/disagg/wan/wan_t2v_disagg_decode.json`
- `configs/disagg/wan_t2v_disagg_controller.json`（示例 Controller 配置）

这些配置**并不只是 `disagg_mode` 不同**。随着角色变化，还会改这些字段：

- `bootstrap_room`
- `sender_engine_rank` / `receiver_engine_rank`
- `decoder_engine_rank` / `decoder_bootstrap_room`
- 某些只对当前角色生效的推理参数

例如，Wan 当前使用的 Decoder 配置是：

```json
// configs/disagg/wan/wan_t2v_disagg_decode.json
```

## 13. 部署启动脚本

```bash
# scripts/server/disagg/wan/start_wan_t2v_disagg.sh

# GPU 分配（Encoder+Decoder 共享 GPU 1，Transformer 独占 GPU 6）
GPU_ENCODER=1
GPU_TRANSFORMER=6
GPU_DECODER=1     # 与 Encoder 共享

# 启动顺序很重要：Decoder → Transformer → Encoder
# 因为上游服务需要连接下游的 RDMA Ring Buffer

# 1. Decoder（port 8006）— 先启动，等待 Phase2 连接
CUDA_VISIBLE_DEVICES=1 python -m lightx2v.server \
    --model_cls wan2.1 --task t2v \
    --config_json configs/disagg/wan/wan_t2v_disagg_decode.json \
    --port 8006 &

# 2. Transformer（port 8003）— 等待 Phase1 连接
CUDA_VISIBLE_DEVICES=6 python -m lightx2v.server \
    --model_cls wan2.1 --task t2v \
    --config_json configs/disagg/wan/wan_t2v_disagg_transformer.json \
    --port 8003 &

# 3. Encoder（port 8002）— 最后启动，连接 Phase1 Ring
CUDA_VISIBLE_DEVICES=1 python -m lightx2v.server \
    --model_cls wan2.1 --task t2v \
    --config_json configs/disagg/wan/wan_t2v_disagg_encoder.json \
    --port 8002 &
```

**启动顺序的原因**：RDMA 连接是**服务端先启动、客户端后连接**的模式。Phase2 的服务端在 Controller/Decoder 侧，Phase1 的服务端在 Controller/Transformer 侧。所以必须从下游到上游依次启动。

**补充一个很容易误解的点**：这个启动脚本并**没有**单独拉起一个常驻 Controller 进程。当前仓库里更常见的使用方式是：

1. 先启动 3 个常驻 HTTP 服务（Decoder → Transformer → Encoder）
2. 再用 `scripts/server/disagg/wan/post_wan_t2v.py` 这种脚本按相同顺序投递请求
3. 最终结果在 Decoder 节点落盘，再由请求脚本轮询 Decoder 的任务状态

## 14. 完整请求流程

```
Controller.run()
 │
 ├─ 创建 3 个 RDMA Ring Buffer（request / phase1 / phase2）
 ├─ 注册服务实例（encoder/transformer/decoder 地址）
 │
 └─ 循环 N 个请求：
      │
      │  ① Controller → request Ring Buffer → Encoder
      │     produce({"prompt": "...", "data_bootstrap_room": 0, ...})
      │
      │  ② Encoder 消费请求，执行编码
      │     T5.infer(prompt) → context
      │     CLIP.visual(image) → clip_out
      │     VAE.encode(image) → vae_out
      │     │
      │     │  写入 RDMA buffer → Mooncake 发送
      │     │  phase1 Ring Buffer 通知 Transformer
      │     ▼
      │
      │  ③ Transformer 消费 phase1 元数据
      │     等待 Mooncake 接收完成（Phase1）
      │     从 buffer 重建 context/clip/vae/latent_shape
      │     SHA256 校验 ✓
      │     │
      │     │  去噪循环：40 步
      │     │  for step in range(40):
      │     │    scheduler.step_pre()
      │     │    transformer.infer()
      │     │    scheduler.step_post()
      │     │  latents = scheduler.latents
      │     │
      │     │  写入 Phase2 buffer → Mooncake 发送
      │     │  phase2 Ring Buffer 通知 Decoder
      │     ▼
      │
      │  ④ Decoder 消费 phase2 元数据
      │     等待 Mooncake 接收完成（Phase2）
      │     从 buffer 重建 latents
      │     SHA256 校验 ✓
      │     │
      │     │  VAE 解码 → save_to_video()
      │     │
      │     │  ⑤ ZMQ 回调 → Controller
      │     │     {"ok": true, "save_path": "/output/video_1.mp4"}
      │     ▼
      │
      └─ Controller 收到所有回调，退出
```

## 15. 思考题

1. **Encoder 和 Decoder 共享一张 GPU。如果 Encoder 正在编码时 Decoder 需要解码，会有冲突吗？**
   - 提示：考虑推理 pipeline 的时序——Encoder 编码完才会触发 Transformer，Transformer 去噪完才会触发 Decoder

2. **SHA256 校验需要 GPU→CPU 拷贝整个张量。对于 200MB 的 VAE 编码结果，这个开销有多大？**
   - 提示：考虑 GPU→CPU 的 DMA 带宽（PCIe 4.0 ≈ 25 GB/s）

3. **RDMA Ring Buffer 的 slot_size 默认 4096 字节。如果请求配置序列化后超过 4092 字节（4096 - 4 字节长度头），会怎样？**
   - 提示：看 `_serialize_config` 的异常处理

4. **当前的 `run()` 循环没有限流——`req_queue + waiting_queue < 2` 是唯一的背压。如果 Encoder 编码很快但 Transformer 去噪很慢，会积压在哪里？**
   - 提示：考虑 Phase1 Ring Buffer 的容量和 Mooncake 传输的阻塞行为

5. **如果要支持多个 Transformer 实例（如 2 张 GPU 各跑一个 Transformer），Controller 的 RDMA Ring Buffer 和 Mooncake 连接需要怎么改？**
   - 提示：当前 Phase1 Ring 是单消费者模型
