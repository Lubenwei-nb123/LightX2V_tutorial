### 1.1 Rank 0 与非 Rank 0 的分工

```
                    ┌──────────────────────────┐
                    │      torchrun 启动       │
                    │  N 个进程, 每个一张 GPU   │
                    └────────┬─────────────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
       ┌──────┴──────┐              ┌──────┴──────┐
       │   Rank 0    │              │  Rank 1..N  │
       │             │              │             │
       │ FastAPI     │              │ worker_loop │
       │ 监听 HTTP   │  broadcast   │ 等待任务    │
       │ 请求        │ ──────────→  │ 数据        │
       │             │  (gloo)      │             │
       │ process_    │              │ process_    │
       │ request()   │  barrier     │ request()   │
       │             │ ←─────────→  │             │
       └─────────────┘              └─────────────┘
```

**关键设计**：只有 Rank 0 运行 FastAPI 和 TaskManager。非 Rank 0 进程通过 `DistributedManager.broadcast_task_data()` 从 Rank 0 接收任务数据（使用 gloo 后端 + pickle 序列化），然后各自在自己的 GPU 上执行推理。

## 5. ServiceContainer：依赖注入

**核心文件**：`lightx2v/server/api/deps.py`

```python
class ServiceContainer:
    _instance: Optional["ServiceContainer"] = None   # 单例

    def __init__(self):
        self.file_service = None
        self.inference_service = None
        self.video_service = None
        self.image_service = None
        self.max_queue_size = 10

    @classmethod
    def get_instance(cls) -> "ServiceContainer":
        if cls._instance is None:
            cls._instance = cls()
        return cls._instance

    def initialize(self, cache_dir, inference_service, max_queue_size=10):
        self.file_service = FileService(cache_dir)
        self.inference_service = inference_service
        self.video_service = VideoGenerationService(self.file_service, inference_service)
        self.image_service = ImageGenerationService(self.file_service, inference_service)
        self.max_queue_size = max_queue_size

def get_services() -> ServiceContainer:
    return ServiceContainer.get_instance()
```

**设计要点**：所有 API handler 通过 `get_services()` 获取服务实例，不直接持有引用。这样 `initialize()` 可以在任意时机调用，handler 注册时不需要服务已就绪。

## 第四部分：任务管理

## 6. TaskManager：任务队列与状态机

**核心文件**：`lightx2v/server/task_manager.py`

TaskManager 是整个服务化的核心调度器，承担三个职责：**维护任务队列**、**驱动状态机流转**、**保证并发安全**。全局只有一个实例（模块末尾 `task_manager = TaskManager()`），由 Rank 0 进程独占使用。

---

### 6.1 数据结构全景

```python
class TaskManager:
    def __init__(self, max_queue_size: int = 100):
        self.max_queue_size = max_queue_size   # 最大活跃任务数（PENDING + PROCESSING）

        # ── 任务存储 ──
        self._tasks: OrderedDict[str, TaskInfo] = OrderedDict()
        #   OrderedDict 保持插入顺序 → FIFO 调度
        #   key = task_id，value = TaskInfo

        # ── 并发控制 ──
        self._lock = threading.RLock()             # 队列锁（可重入）
        self._processing_lock = threading.Lock()   # 推理互斥锁
        self._current_processing_task: Optional[str] = None

        # ── 统计计数器 ──
        self.total_tasks = 0       # 历史总任务数
        self.completed_tasks = 0   # 成功完成数
        self.failed_tasks = 0      # 失败数
```

**TaskInfo 数据结构**（每个任务一份）：

```python
@dataclass
class TaskInfo:
    task_id: str                         # 唯一 ID（来自请求或自动生成）
    status: TaskStatus                   # 当前状态（枚举）
    message: Any                         # 原始请求对象（VideoTaskRequest / ImageTaskRequest）
    start_time: datetime                 # 任务创建时间（非推理开始时间）
    end_time: Optional[datetime] = None  # 完成/失败/取消时间
    error: Optional[str] = None          # 失败原因（仅 FAILED 状态有值）
    save_result_path: Optional[str] = None  # 输出文件路径（仅 COMPLETED 有值）
    stop_event: threading.Event = field(default_factory=threading.Event)
    #   取消信号：set() 表示请求取消，is_set() 用于检查
    thread: Optional[threading.Thread] = None  # 保留字段，当前未使用
```

**状态枚举**：

```python
class TaskStatus(Enum):
    PENDING    = "pending"     # 已入队，等待处理
    PROCESSING = "processing"  # 正在推理
    COMPLETED  = "completed"   # 推理完成
    FAILED     = "failed"      # 推理出错
    CANCELLED  = "cancelled"   # 用户取消
```

### 6.2 任务状态机

```
  ┌────────────────────────────────────────────────────────────────────┐
  │                                                                    │
  │  HTTP POST                                                         │
  │  /v1/tasks/video    ──► create_task()                              │
  │                              │                                     │
  │                              ▼                                     │
  │                      ┌──────────────┐                              │
  │                      │   PENDING    │ 已入队，等待调度线程取走       │
  │                      └──────┬───────┘                              │
  │                             │                                      │
  │            守护线程          │ start_task()                         │
  │            取出任务          │ 状态迁移 + move_to_end()             │
  │                             ▼                                      │
  │                      ┌──────────────┐                              │
  │                      │  PROCESSING  │ GPU 正在推理                  │
  │                      └──┬───────┬───┘                              │
  │                         │       │                                  │
  │           complete_task()│       │fail_task()                      │
  │                         │       │（推理报错 / 取消后的清理）         │
  │                         ▼       ▼                                  │
  │              ┌───────────┐   ┌────────┐                            │
  │              │ COMPLETED │   │ FAILED │                            │
  │              └───────────┘   └────────┘                            │
  │                                                                    │
  │  DELETE /v1/tasks/{id}        cancel_task()                        │
  │       │                           │                                │
  │       │  PENDING ────────────────►│──► CANCELLED                   │
  │       │  PROCESSING ─────────────►│──► CANCELLED（stop_event.set）  │
  │       │  COMPLETED / FAILED ─────►│  不可取消，返回 False           │
  │                                                                    │
  └────────────────────────────────────────────────────────────────────┘
```

**关键细节**：`start_task()` 调用了 `self._tasks.move_to_end(task_id)`，将正在处理的任务移到 OrderedDict 末尾。这样 `get_next_pending_task()` 的遍历从头开始扫描，始终能快速找到最早的 PENDING 任务，而不会被 PROCESSING 任务干扰。

### 6.3 并发控制：双锁机制

TaskManager 同时面对两类并发竞争：
1. **多个 HTTP 请求**并发调用 `create_task`、`get_task_status` 等队列操作
2. **守护线程**调用 `start_task`、`complete_task` 等状态变更

框架用**两把粒度不同的锁**分别应对：

```python
self._lock = threading.RLock()            # 队列锁：保护 _tasks 字典
self._processing_lock = threading.Lock()  # 推理锁：保护 GPU 推理资源
```

```
                    HTTP 线程池                    守护线程
                         │                            │
          create_task()  │  get_task_status()          │  start_task()
                         │                            │  complete_task()
                         ▼                            ▼
               ┌─────────────────────────────────────────┐
               │           _lock (RLock)                 │
               │   保护 _tasks OrderedDict 的读写         │
               │   持有时间：微秒级（dict 操作）            │
               └─────────────────────────────────────────┘

               ┌─────────────────────────────────────────┐
               │       _processing_lock (Lock)           │
               │   保护 GPU 推理资源                      │
               │   持有时间：秒到分钟级（整个推理过程）    │
               └─────────────────────────────────────────┘
```

**为什么 `_lock` 用 RLock（可重入锁）？**

`cancel_task()` 内部会调用 `task.stop_event.set()`，同时需要持有 `_lock`。而 `cancel_all_tasks()` 会在持有 `_lock` 的情况下遍历并调用 `cancel_task()`——形成了**同一线程的递归加锁**。RLock 允许同一线程重复获取同一把锁，普通 Lock 会在此处死锁。

**为什么 `_processing_lock` 用普通 Lock？**

推理锁只需要"任意时刻只有一个任务持有"这个语义，不需要重入。用普通 Lock 语义更清晰，也避免了意外的重入场景。

### 6.4 `create_task()`：入队与限流

```python
# task_manager.py:47-64
def create_task(self, message: Any) -> str:
    with self._lock:
        # ① 幂等校验：相同 task_id 不重复入队
        if hasattr(message, "task_id") and message.task_id in self._tasks:
            raise RuntimeError(f"Task ID {message.task_id} already exists")

        # ② 队列满检查（只计 PENDING + PROCESSING，不计历史任务）
        active_tasks = sum(
            1 for t in self._tasks.values()
            if t.status in [TaskStatus.PENDING, TaskStatus.PROCESSING]
        )
        if active_tasks >= self.max_queue_size:
            raise RuntimeError(f"Task queue is full (max {self.max_queue_size} tasks)")
            # → 上层 API 捕获此异常，返回 HTTP 503

        # ③ 创建 TaskInfo，写入 OrderedDict
        task_id = getattr(message, "task_id", str(uuid.uuid4()))
        task_info = TaskInfo(
            task_id=task_id,
            status=TaskStatus.PENDING,
            message=message,
            save_result_path=getattr(message, "save_result_path", None),
        )
        self._tasks[task_id] = task_info
        self.total_tasks += 1

        # ④ 顺带触发历史清理（避免 dict 无限增长）
        self._cleanup_old_tasks()

        return task_id
```

**限流逻辑的边界**：`max_queue_size` 限制的是 `PENDING + PROCESSING` 的**活跃任务**总数，不包含已完成的历史任务。默认值 100（TaskManager 初始化时），但 `ApiServer` 用 `server_config.max_queue_size`（默认 10）初始化，并通过 `ServiceContainer.initialize()` 透传给队列——实际生效的是 10。

### 6.5 `get_next_pending_task()`：FIFO 调度

```python
# task_manager.py:177-182
def get_next_pending_task(self) -> Optional[str]:
    with self._lock:
        for task_id, task in self._tasks.items():
            if task.status == TaskStatus.PENDING:
                return task_id       # 返回第一个 PENDING 任务的 ID
    return None
```

这是**纯 FIFO**：遍历 OrderedDict（保持插入顺序），返回第一个 PENDING 任务。没有优先级，没有抢占。守护线程每秒调用一次，取到后立即进入 `_process_single_task`。

---

### 6.6 `start_task()` / `complete_task()` / `fail_task()`：状态驱动

```python
# task_manager.py:66-77
def start_task(self, task_id: str) -> TaskInfo:
    with self._lock:
        task = self._tasks[task_id]
        task.status = TaskStatus.PROCESSING
        task.start_time = datetime.now()     # 覆盖为推理实际开始时间
        self._tasks.move_to_end(task_id)    # ← 移到末尾，PENDING 扫描跳过它
        return task

# task_manager.py:79-89
def complete_task(self, task_id: str, save_result_path: Optional[str] = None):
    with self._lock:
        task = self._tasks[task_id]
        task.status = TaskStatus.COMPLETED
        task.end_time = datetime.now()
        if save_result_path:
            task.save_result_path = save_result_path
        self.completed_tasks += 1

# task_manager.py:93-104
def fail_task(self, task_id: str, error: str):
    with self._lock:
        task = self._tasks[task_id]
        task.status = TaskStatus.FAILED
        task.end_time = datetime.now()
        task.error = error
        self.failed_tasks += 1
```

### 6.7 `acquire_processing_lock()` / `release_processing_lock()`：推理互斥

```python
# task_manager.py:159-175
def acquire_processing_lock(self, task_id: str, timeout: Optional[float] = None) -> bool:
    acquired = self._processing_lock.acquire(
        timeout=timeout if timeout else False
    )
    if acquired:
        with self._lock:
            self._current_processing_task = task_id
            logger.info(f"Task {task_id} acquired processing lock")
    return acquired

def release_processing_lock(self, task_id: str):
    with self._lock:
        if self._current_processing_task == task_id:
            self._current_processing_task = None
            try:
                self._processing_lock.release()
            except RuntimeError as e:
                logger.warning(f"Task {task_id} tried to release lock but failed: {e}")
```

**`timeout=1` 的含义**：守护线程调用时传 `timeout=1`，意思是"最多等 1 秒获取锁"。在正常情况下只有一个守护线程，`_processing_lock` 总是空闲的，会立即获取成功。这个超时是防御性设计，避免极端情况下的死锁。

**`release_processing_lock` 的防御**：释放时先检查 `_current_processing_task == task_id`，防止一个任务错误地释放另一个任务的锁（例如异常路径下的 finally 块重复调用）。

### 6.8 任务取消机制：`cancel_task()`

```python
# task_manager.py:106-124
def cancel_task(self, task_id: str) -> bool:
    with self._lock:
        task = self._tasks.get(task_id)
        if not task:
            return False

        # 终态任务不可取消
        if task.status in [TaskStatus.COMPLETED, TaskStatus.FAILED]:
            return False

        # 发出取消信号
        task.stop_event.set()
        task.status = TaskStatus.CANCELLED
        task.end_time = datetime.now()
        task.error = "Task cancelled by user"

        # 等待处理线程退出（最多 5 秒）
        if task.thread and task.thread.is_alive():
            task.thread.join(timeout=5)

        return True
```

**`stop_event` 的传播路径**：

```
cancel_task()
  └─ task.stop_event.set()
        │
        ├─ _process_single_task()  ← 推理前检查（若此时推理未开始，直接取消）
        │    if task_info.stop_event.is_set(): fail_task(); return
        │
        └─ generate_with_stop_event()  ← 图片下载/处理各环节前检查
             if stop_event.is_set(): return None
```

**取消的局限性**：`runner.run_pipeline()` 本身是同步阻塞调用，内部不检查 `stop_event`。这意味着：
- **若任务在 PENDING 状态被取消**：下次调度线程扫到时状态已是 CANCELLED，直接跳过，取消立即生效。
- **若任务在 PROCESSING 状态被取消**：`stop_event` 被置位，但推理不会中断。等到当前推理完成后，`complete_task` 会正常调用，状态从 CANCELLED 变为 COMPLETED（注意：`complete_task` 不检查任务是否已被取消）。

这是一个已知的设计取舍——完全中断 GPU 推理需要更复杂的机制（如 CUDA Context 销毁或协程 cancellation），当前实现选择了简单性。

### 6.9 `get_service_status()`：可观测性接口

```python
# task_manager.py:184-199
def get_service_status(self) -> Dict[str, Any]:
    with self._lock:
        active_tasks = [
            task_id for task_id, task in self._tasks.items()
            if task.status == TaskStatus.PROCESSING
        ]
        pending_count = sum(
            1 for t in self._tasks.values()
            if t.status == TaskStatus.PENDING
        )
        return {
            "service_status": "busy" if self._current_processing_task else "idle",
            "current_task": self._current_processing_task,   # 当前推理任务 ID
            "active_tasks": active_tasks,                    # PROCESSING 任务列表
            "pending_tasks": pending_count,                  # 排队数
            "queue_size": self.max_queue_size,               # 队列上限
            "total_tasks": self.total_tasks,
            "completed_tasks": self.completed_tasks,
            "failed_tasks": self.failed_tasks,
        }
```

这个接口对应 `GET /v1/service/status`，是运维监控的核心入口。`"busy"/"idle"` 由 `_current_processing_task` 是否为 None 决定（而不是 PROCESSING 任务数），确保了状态的单一来源。

### 6.10 历史任务清理：`_cleanup_old_tasks()`

```python
# task_manager.py:201-212
def _cleanup_old_tasks(self, keep_count: int = 1000):
    if len(self._tasks) <= keep_count:
        return   # 未超限，直接返回

    # 只清理已结束的任务（COMPLETED / FAILED / CANCELLED）
    completed_tasks = [
        (task_id, task) for task_id, task in self._tasks.items()
        if task.status in [TaskStatus.COMPLETED, TaskStatus.FAILED, TaskStatus.CANCELLED]
    ]
    # 按结束时间升序（最早完成的先清理）
    completed_tasks.sort(key=lambda x: x[1].end_time or x[1].start_time)

    remove_count = len(self._tasks) - keep_count
    for task_id, _ in completed_tasks[:remove_count]:
        del self._tasks[task_id]
        logger.debug(f"Cleaned up old task: {task_id}")
```

**清理时机**：每次 `create_task()` 末尾触发一次。不是定时清理，而是**"写入时触发"**——因为只有写入新任务时才会让 dict 超限。

**清理策略**：只删除终态任务（COMPLETED / FAILED / CANCELLED），绝不删除 PENDING 或 PROCESSING 任务。按结束时间从旧到新清理，保留最近的历史记录。

### 6.11 调度线程与 TaskManager 的协作全图

```
  ┌────────────────────────┐         ┌─────────────────────────────────────┐
  │   FastAPI 异步事件循环  │         │         守护线程（_task_processing_loop）│
  │   (uvicorn, 多协程)    │         │         独立 asyncio 事件循环          │
  └───────────┬────────────┘         └──────────────────┬──────────────────┘
              │                                         │
  POST /v1/tasks/video/              while not stop:
              │                        task_id = get_next_pending_task()
              ▼                        if task_id is None: sleep(1); continue
  create_task(message)                 │
    ├─ 检查队列                        ▼
    ├─ 写 _tasks (持有 _lock)       loop.run_until_complete(
    └─ 返回 task_id                   _process_single_task(task_info))
              │                        │
              │                        ├─ acquire_processing_lock(timeout=1)
  立即返回     │                        │      ← 写 _current_processing_task
  HTTP 200    │                        ├─ start_task()
              │                        │      ← 写 status=PROCESSING
              │                        │      ← move_to_end()
              │                        │
  GET /v1/tasks/{id}/status           ├─ await generation_service.generate(...)
    ├─ get_task_status()              │      ← 下载图片 / 推理 / 保存文件
    │   持有 _lock（微秒）            │      （整个过程持有 _processing_lock）
    └─ 返回当前 status                │
              │                        ├─ complete_task() / fail_task()
              │                        │      ← 写 status=COMPLETED/FAILED
              │                        │
  DELETE /v1/tasks/{id}               └─ release_processing_lock()
    ├─ cancel_task()                         ← 清 _current_processing_task
    │   持有 _lock
    │   stop_event.set()
    └─ 返回 stop_status
```

**线程安全边界总结**：

| 操作 | 调用方 | 持有锁 | 持有时间 |
|------|--------|--------|---------|
| `create_task` | FastAPI 协程（事件循环线程） | `_lock` | 微秒级 |
| `get_task_status` | FastAPI 协程 | `_lock` | 微秒级 |
| `cancel_task` | FastAPI 协程 | `_lock` | 微秒级 |
| `get_next_pending_task` | 守护线程 | `_lock` | 微秒级 |
| `start_task` | 守护线程 | `_lock` | 微秒级 |
| `complete_task` / `fail_task` | 守护线程 | `_lock` | 微秒级 |
| `acquire_processing_lock` | 守护线程 | `_processing_lock` | 秒到分钟级（整个推理） |

两类线程的竞争点只在 `_lock` 上，而 `_lock` 的持有时间极短（dict 操作），不会造成可感知的延迟。推理耗时全部隔离在 `_processing_lock` 下，不影响 API 响应。

        # 3. 更新 input_info（复用模板，避免重复创建）

        self.runner.set_config(task_data)

        # 5. 执行推理
        self.runner.run_pipeline(self.input_info)

        # 6. [多卡] 同步
        if self.world_size > 1:
            self.dist_manager.barrier()

        return {"task_id": ..., "status": "success", "save_result_path": ...}

## 11. DistributedManager：多卡通信

**核心文件**：`lightx2v/server/services/distributed_utils.py`

### 11.1 任务数据广播

多卡推理时，只有 Rank 0 接收 HTTP 请求。其他 Rank 通过 `broadcast_task_data` 获取任务数据。

```python
def broadcast_task_data(self, task_data=None):
    if self.is_rank_zero():
        # 发送端
        if task_data is None:
            stop_signal = torch.tensor([1])     # 停止信号
        else:
            stop_signal = torch.tensor([0])     # 正常任务
        dist.broadcast(stop_signal, src=0, group=self.task_pg)

        if task_data is not None:
            task_bytes = pickle.dumps(task_data)
            task_length = torch.tensor([len(task_bytes)])
            dist.broadcast(task_length, src=0, group=self.task_pg)
            self._broadcast_byte_chunks(task_bytes)  # 分块传输
        return task_data
    else:
        # 接收端
        stop_signal = torch.tensor([0])
        dist.broadcast(stop_signal, src=0, group=self.task_pg)
        if stop_signal.item() == 1:
            return None                         # 收到停止信号

        task_length = torch.tensor([0])
        dist.broadcast(task_length, src=0, group=self.task_pg)
        task_bytes = self._receive_byte_chunks(task_length.item())
        return pickle.loads(task_bytes)
```

**为什么用 gloo 而不用 nccl？**

任务数据是 Python dict（包含字符串、列表等），需要 pickle 序列化为字节流，然后用 `torch.uint8` tensor 传输。gloo 后端支持 CPU tensor 的 broadcast，而 nccl 只支持 CUDA tensor。任务数据量很小（几 KB），gloo 的性能足够。

**为什么分块传输？**（`_broadcast_byte_chunks`）

单次 broadcast 的 tensor 太大可能导致超时（gloo 的默认超时较短）。分块（1MB/块）可以避免这个问题。

| `lightx2v_worker_request_failure` | Counter | 失败请求数（按 error_type 分标签） |
| `lightx2v_worker_request_duration` | Histogram | 总推理耗时（按 model_cls） |
| `lightx2v_run_text_encode_duration` | Histogram | 文本编码耗时 |
| `lightx2v_run_img_encode_duration` | Histogram | 图像编码耗时 |
| `lightx2v_run_vae_decode_duration` | Histogram | VAE 解码耗时 |
| `lightx2v_run_per_step_dit_duration` | Histogram | 每步 DiT 耗时（按 step_no/total_steps） |

**Monitor** 是线程安全的单例（`__new__` + `threading.Lock`），在 Runner 的各个阶段通过 `monitor.lightx2v_xxx.observe(duration)` 记录耗时。
